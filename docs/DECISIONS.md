# 기술 결정 기록 (ADR)

기준일 2026-09-09 / 기획서 `SPEC_v1.0.md` 기준
프로젝트 성격: **실제 파일럿·제품 트랙 + 경진대회·졸업작품 트랙 혼합**
현장 데이터: **없음 — 공개 권고 데이터(실데이터) + 합성 자산**

이 조합이 전체 결정을 지배한다. **권고 측은 100% 실제 공개 데이터**로 가져가서 제품
신뢰성을 확보하고, **자산 측만 합성**하되 실제 제품 식별자에 앵커해서 판정이 진짜
판정이 되게 한다 (ADR-006).

## ADR-001 · 언어와 프레임워크 → Python + FastAPI

**결정**: 백엔드 전체를 Python 3.11+ / FastAPI로 통일한다. Spring Boot는 기각.

**근거**
- 기획서 표 27이 이미 **Ingestion을 "Python Worker와 Scheduler"로 못박았다**. 수집이
  Python인데 API가 Java면 정규화 규칙·버전 비교기·조건식 트리가 두 언어에 중복 구현된다.
  적용성 엔진은 수집과 같은 자료구조를 공유해야 하는 코어다.
- 다뤄야 할 형식이 전부 Python 생태계가 강한 영역이다: CSAF/CVE JSON, EPSS CSV,
  OVAL XML, PCAP. 버전 범위 비교는 `univers`·`packaging`이 이미 여러 scheme(SemVer, RPM
  epoch, DEB, generic)을 구현해 두었고, 이게 R03(버전 문법 다양성) 대응의 출발점이다.
- 1인~소수 인력 기준으로 언어 하나가 압도적으로 유리하다.

**기각 사유 (Spring Boot)**: 사내 Java 표준이 있거나 기존 SI 자산을 재사용해야 할 때만
정당하다. 지금은 해당 없음. 나중에 SI 제안으로 갈 때도 API 계층만 얇게 감싸면 되고,
판정 커널은 언어 중립적인 규칙 DSL + JSON 입출력으로 유지한다.

## ADR-002 · 그래프 저장소 → PostgreSQL 단독, Neo4j 미도입

**결정**: `topology_edge`를 PostgreSQL에 저장하고, 경로 계산은 **Python 인메모리 그래프**로
수행한다. Neo4j는 도입하지 않는다.

**근거**
- 규모가 작다. NFR-PERF-002는 **5홉 / 10만 엣지 / p95 5초**다. 10만 엣지는 그래프
  데이터베이스가 필요한 규모가 아니다 — 인메모리로 전부 올라간다.
- 더 중요한 이유: 이 경로 엔진은 **단순 도달성 탐색이 아니다.** 기획서 10.1은 "각 취약점의
  전제조건을 상태 전이로 평가"하라고 한다. 즉 엣지를 따라가면서 인증·권한·기능 활성
  여부를 상태로 들고 다녀야 한다. 이건 Cypher로 짜면 읽을 수 없는 쿼리가 되고,
  애플리케이션 로직으로 짜면 **단위 테스트가 가능하다.** 확신도 계산(최약 엣지 + 증거
  신선도)도 마찬가지다.
- 폐쇄망(NFR-OFF-001)에서 서비스가 하나 늘어난다. Neo4j는 Community/Enterprise 라이선스
  구분이 있어 번들 배포 시 검토 부담이 붙는다.

**재검토 트리거**: 실제 벤치마크에서 10만 엣지 5홉 p95가 5초를 넘거나, 엣지가 100만
규모로 커질 때. 그 전에는 도입하지 않는다.

## ADR-003 · 슬라이스 1 저장소 → SQLite, 스키마는 PostgreSQL 호환

**결정**: 슬라이스 1(CLI)은 SQLite로 돌린다. 단, DDL은 PostgreSQL과 호환되게 쓰고
JSONB 자리는 JSON 텍스트 컬럼으로 둔다.

**근거**: CLI 데모에 Postgres 서비스를 띄우게 하면 테스트가 느려지고 진입 장벽이 생긴다.
슬라이스 1의 산출물은 판정 로직이지 운영 인프라가 아니다.

**전환 경계**: **웹 UI가 붙거나 동시 쓰기 주체가 둘 이상 생기는 시점**에 PostgreSQL로
넘어간다. 그때까지 Postgres 전용 문법(JSONB 연산자, 파티셔닝)을 쓰지 않는다.

> **후속**: ADR-011 이 트리거를 좁혔고, ADR-027 에서 그 조건이 충족되어 전환했다.
> 지금은 웹앱이 PostgreSQL, CLI 가 SQLite 다. Postgres 전용 문법은 여전히 쓰지 않는다.

## ADR-004 · 첫 슬라이스 → "판정 커널" CLI

**결정**: 첫 산출물은 웹 UI도 그래프도 아닌, **자산 1건 + 권고 1건 → 적용성 판정 카드**를
출력하는 CLI다.

**근거 — 기획서가 두 번 같은 답을 준다**
- **부록 D**가 `decide_applicability()` 의사코드를 그대로 제공한다. 구현할 함수가 이미 적혀 있다.
- **22장 3주차**: "기술 스파이크 | CSAF NVD KEV 수집 버전 DSL 원문 해시 제품 별칭 |
  **CLI Notebook 데모**". 기획서 자신이 첫 기술 산출물을 CLI로 지정했다.

**위험 정렬**: 위험 등록부 상위 4개(R01 자산 정보 부족, R02 별칭 오매칭, R03 버전 문법,
R04 비정형 권고)가 **전부 이 슬라이스 안에 있다.** UI나 그래프에는 최상위 위험이 없다.
가장 깨지기 쉬운 것을 인프라 없이 먼저 깬다.

### 슬라이스 1 구성 (우선순위 순)

| # | 구성요소 | 왜 이 순서인가 |
|---|---|---|
| a | **scheme별 버전 비교기 + 삼진 조건식 트리** | R03. 인프라 0, property test 가능. 여기가 틀리면 나머지 전부 무의미 |
| b | **CSAF 2.0 파서** (product_tree / product_status / version_range) | 실데이터 진입점. 원문 해시 + `raw_expression` 보존 |
| c | **`resolve_product`** — 식별 수준(Exact~Inferred) + confidence 반환 | R02 |
| d | **`decide_applicability`** → 9개 상태 | 부록 D 그대로 |
| e | **assertion append 저장 + `as_of` 재현** | 덮어쓰기 금지, 재현성 100% |

### 완료 정의 (Definition of Done)

```
# 경계 골드셋 (ADR-006 자산 A) - 기대: affected_confirmed
python -m otai decide \
  --asset    fixtures/assets/melsec-iqr-fw48.json \
  --advisory data/csaf/cisa/2026/icsa-26-036-02.json \
  --as-of    2026-09-09

# 부록 C 예시 자산(가상 벤더) - 기대: no_known_match ("안전" 표현 금지 검증)
python -m otai decide \
  --asset    fixtures/assets/plc-l2-014.json \
  --advisory data/csaf/cisa/2026/icsa-26-036-02.json \
  --as-of    2026-09-09
```

출력 = **판정 카드**, 아래를 모두 포함:
1. 9개 상태 중 하나 (코드 + 부록 B 한국어 문구)
2. **결론을 바꾼 조건** (decisive conditions) — 점수가 아니라 조건
3. 일치 / 불일치 / **누락** 필드 3분류
4. 근거: advisory id, `raw_expression` 원문, 소스 콘텐츠 해시
5. `input_hash` + `rule_version` + `as_of`
6. `insufficient_information`이면 **다음 최적 질문** 1개

**게이트 3개**
- 같은 입력 2회 실행 → **바이트 동일 출력** (NFR-EXP-001).
  → 출력에 **wall-clock 시각을 넣지 않는다.** 시간은 `as_of`와 `observed_at`만 등장한다.
  실행 시각이나 `ingested_at`이 판정 카드에 새면 이 게이트는 첫날 깨진다.
- 경계 케이스 골드셋에서 **false safe 0건** (ADR-006)
- 과거 `--as-of`로 과거 판정 재현

### 슬라이스 1 명시적 제외

웹 UI · 공격 경로 엔진 · 우선순위 엔진(P0~P4) · KEV/EPSS · OCR · PCAP · 다중 벤더 확장.

> KEV/EPSS를 뺀 이유: 둘은 **정렬 신호이지 적용성 입력이 아니다.** 적용성이 확정되기
> 전에 붙이면 "심각도 높으니 조치" 라는 기존 도구의 실패 모드를 그대로 재현하게 된다.

## ADR-005 · 첫 소스 → CISA OT CSAF + Siemens ProductCERT CSAF (2개)

**결정**: 벤더 2~3개를 고르는 대신 **성격이 다른 CSAF 공급자 2곳**을 고른다.

### 검증 결과 (2026-09-09 실측)

| 소스 | 확인된 엔드포인트 | 성격 |
|---|---|---|
| **CISA (coordinator)** | `github.com/cisagov/CSAF` → `csaf_files/OT/white/<연도>/icsa-*.json` | 폭. git clone 가능 → **폐쇄망 번들에 그대로 적합** |
| **Siemens ProductCERT (vendor)** | `cert-portal.siemens.com/productcert/csaf/provider-metadata.json` → ROLIE 피드 `ssa-feed-tlp-white.json` | 벤더 권위. 항목별 **해시·서명 파일 동봉** |

- Siemens 피드는 **2026-09-08 갱신 확인** (라이브). 항목별 해시·서명 파일이 함께 제공되어
  FR-SRC-004(원문 해시), FR-SRC-006(서명 검증)을 실데이터로 바로 만족시킬 수 있다.
- CISA CSAF는 `document.publisher.category = "coordinator"`, product_tree는
  vendor / product_name / product_version 3단 분기, `product_status.known_affected` 사용.

### 이 조합을 고른 진짜 이유

**CISA가 자체 CSAF를 내지 않는 벤더까지 커버한다** — 실제로 확인했다:

> `icsa-26-036-02.json` = **Mitsubishi Electric** MELSEC iQ-R Series.
> Mitsubishi는 자체 CSAF 피드가 확인되지 않지만 CISA를 통해 기계 판독 가능한 형태로 들어온다.
> LS ELECTRIC도 CISA 권고가 존재한다 (ICSA-22-228-02, ICSA-23-040-02 — 다만 2022~23년
> 건이라 CSAF 저장소 연도 커버리지는 별도 확인 필요).

이게 **한국 스마트팩토리 벤더 분포(Mitsubishi, LS ELECTRIC, Omron)를 CSAF 파서 하나로
다룰 수 있게 해주는 경로**다. 제품 트랙의 확장성이 여기서 나온다.

그리고 **두 소스가 겹치는 구간이 곧 데모다.** 같은 Siemens SSA를 CISA와 Siemens가 다르게
기술하면, 표 13(필드별 권위: 제품 영향은 벤더 우선)과 FR-SRC-005(충돌 보존, 자동 덮어쓰기
금지)를 **실데이터로** 보여줄 수 있다. 이건 표 44의 차별화 축 두 개를 한 화면에서 증명한다.

### 실데이터가 던진 숙제 — 이미 확인된 것

`icsa-26-036-02`의 영향 버전은 구조화된 범위 객체가 아니라 **문자열 `"<=48"`** 이다.
제품명은 **`"MELSEC iQ-R Series R08/16/32/120PCPU firmware"`** — 모델 4개가 한 문자열에 들어 있다.

Siemens는 정반대다. `ssa-019113.json` 확인 결과:

> 버전 범위를 **`vers:` URI 문법**으로 표현한다 — `"vers:intdot/>=3.1.6|<3.1.7"`.
> 그리고 `product_identification_helper.model_numbers`에 **주문번호**를 준다
> (`"6ES7518-4AX00-1AB0"`).

**두 소스가 서로 다른 문법을 쓴다.** 비교기는 첫날부터 입력 문법 2종(`vers:` URI /
자유 문자열)을 받아야 한다. 이건 슬라이스 1(a)의 설계를 바꾼다 — 파서가 문법을 판별해
공통 범위 표현으로 정규화하되 `raw_expression`은 양쪽 다 원문 그대로 보존한다.

식별 수준(표 18)도 실데이터에서 갈린다:

| 소스 | 주는 것 | 도달 가능한 식별 수준 |
|---|---|---|
| Siemens | 주문번호 `6ES7518-4AX00-1AB0` | **Exact** — 자동 연결 가능 |
| CISA / Mitsubishi | 제품명 문자열뿐 | **Composite~Fuzzy** — 사람 확인 필요 |

즉 R03(버전 문법)과 R02(별칭·모델 분해)는 가설이 아니라 **첫 파일부터 터지는 문제**이고,
동시에 표 18의 식별 수준 사다리를 **합성 없이 실데이터로 시연할 수 있다는 뜻**이다.
`raw_expression` 보존과 scheme별 비교기 설계가 옳았다는 확증이자, 슬라이스 1이 반드시
이 둘로 시작해야 하는 이유다.

## ADR-006 · 자산 데이터 → 실제 제품 식별자에 앵커된 합성 자산

**결정**: 현장 데이터가 없으므로 자산은 합성한다. 단 **아무렇게나 만들지 않고, 실제 권고
파일에서 제품 식별자와 경계 버전을 역으로 추출해서** 부록 C 형식으로 생성한다.

**방법**: `icsa-26-036-02`가 "MELSEC iQ-R … firmware `<=48` 영향, 49에서 수정"이라고
말하면, 그 경계를 둘러싼 자산을 만든다.

| 합성 자산 | 펌웨어 | 기대 판정 | 검증하는 것 |
|---|---|---|---|
| A | 48 | `affected_confirmed` | 경계 포함 |
| B | 49 | `not_affected_confirmed` / `fixed` | 경계 배제 |
| C | `unknown` | `insufficient_information` | **unknown을 false로 붕괴시키지 않음** |
| D | 47, 모델만 일치 (R08 여부 미상) | `affected_likely` | 부분 추론 |
| E | 다른 벤더 | `no_known_match` | **"안전"으로 표시하지 않음** |

**이게 왜 결정적인가**: 정답이 **권고문 자체에서 파생**되므로, 현장 전문가 2인 라벨링
(기획서 18.1) 없이도 **객관적으로 옳은 골드셋**을 만들 수 있다. 현장 데이터 부재라는
제약을 우회하는 유일한 길이고, 동시에 R03 property test의 입력이 된다.

**한계 (명시할 것)**: 이 골드셋은 **적용성**만 검증한다. 도달성·공정 영향·정비 가능성은
현장 증거로만 얻을 수 있고 외부 소스로 대체 불가하다(표 13). 따라서 공격 경로와 P0~P4의
정확도는 이 방식으로 주장할 수 없다 — 합성 토폴로지 위에서 **로직 시연**까지만 가능하다.
논문이나 대회 발표에서 이 선을 넘지 않는다.

## ADR-007 · 도달성 미상 → `P?` 버킷과 보류된 강제규칙

**결정**: 강제규칙 H01~H05 의 전제조건이 미상이면 **규칙을 발화시키지도, 무시하지도
않는다.** 항목을 `P?` 버킷에 넣고 "무엇이 확인되면 어느 등급이 되는지"를 함께 기록한다.

**문제**: H01~H04 가 전부 경로 정보를 요구하는데 경로 엔진은 슬라이스 3이다.

| 안 | 동작 | 대가 |
|---|---|---|
| A 보수적 | 미상 = 도달 가능 가정 | P0/P1 폭증, 행동 큐가 무의미 |
| B 낙관적 | 미상 = 미도달 가정 | **우선순위판 false safe** |
| **C 분리** | `P?` 별도 트랙, 강제규칙 보류 | 버킷 하나 증가 |

**C 채택** (사용자 결정). B 는 불변 규칙 1의 정신에 정면으로 어긋나고, A 는 제품을
못 쓰게 만든다. C 는 unknown 을 정상 상태로 다루는 이 제품의 설계 철학과 일치한다.

### `P?` 의 의미 — 표 24 의 슬라이스 2 확장

`P?` 는 "낮은 우선순위"가 아니라 **"막힌 P0/P1"** 이다. P3(확인 또는 모니터)와 다르다:
P3 은 도달성이 낮다고 *판단된* 것이고, `P?` 는 판단 자체가 불가능한 것이다.

각 항목은 `floor_if_confirmed` 를 함께 갖는다 — 전제조건이 확인되면 최소 어느 등급이
되는지. 행동 큐 정렬은 **`P0` → `P?`(floor 순) → `P1` → `P2` → `P3` → `P4`**.

이것은 슬라이스 1의 "다음 최적 질문"을 우선순위에 적용한 것이다. 판정에서 정보가
없으면 질문을 돌려주듯, 우선순위에서도 막힌 이유와 풀 방법을 돌려준다.

### 구현하며 추가된 제약 — `P?` 는 적용성 확정 뒤에만 붙는다

첫 구현에서 큐 10건 중 **6건이 `P?`** 가 되었다. H02 의 전제조건이 전부 미상이면
"확인하면 P0 일 수도"가 되는데, 적용성조차 미확정인 항목까지 그렇게 표시되면서
행동 큐가 무의미해졌다 — **결정 C 가 피하려던 바로 그 실패 모드**(A안의 P0 폭증)가
다른 경로로 재현된 것이다.

**규칙 추가**: 강제규칙에 `적용성` 전제조건이 있고 그것이 TRUE 가 아니면 보류하지
않는다. 적용성이 미상일 때 올바른 다음 행동은 **적용성 확인**이고, 그것은 이미 판정
카드의 '다음 최적 질문'이 말하고 있다. 도달성을 묻는 것은 그다음이다.

적용 후 `P?` 는 10건 중 3건으로 줄었고, 셋 다 적용성이 확정된 항목이다.
`tests/test_priority.py::test_pending_track_stays_a_minority` 가 이 성질을 지킨다.

### 도달성의 세 층위 — 전부 미상은 아니다

부록 A 의 자산 필드가 이미 **자산 단위 노출**을 담는다. 경로 엔진 없이도 평가된다.

| 전제조건 | 슬라이스 2 근거 | 상태 |
|---|---|---|
| 원격접속 경계 자산 (H04) | `network.remote_access` | 평가 가능 |
| 무인증 원격 쓰기 (H02) | `protocols[]` 에 Modbus TCP/502 server + 비암호화 | 평가 가능 (표 4 Exposure Pattern) |
| 공정 안전 영향 (H03) | `operations.safety_criticality` | 평가 가능 |
| 수명주기 (H04) | `lifecycle_status` | 평가 가능 |
| **유효 경로 (H01)** | 멀티홉 토폴로지 | **UNKNOWN → 슬라이스 3** |
| **중요 자산에 도달 (H02)** | 멀티홉 토폴로지 | **UNKNOWN → 슬라이스 3** |
| **외부 상위 Zone 도달 (H03)** | 멀티홉 토폴로지 | **UNKNOWN → 슬라이스 3** |

각 규칙은 **이름 붙은 전제조건에 대한 삼진 논리 논리곱**으로 구현한다. 판정 카드는
어느 전제조건이 TRUE/FALSE/UNKNOWN 이었는지 나열한다. 슬라이스 3 은 규칙 엔진을
건드리지 않고 UNKNOWN 자리만 채운다.

## ADR-008 · P0~P4 정확도는 주장하지 않는다

**결정**: 우선순위의 **정확도를 주장하지 않는다.** 검증은 세 가지로 대체한다.

1. **규칙 발화 표** — H01~H05 × 각 전제조건이 UNKNOWN 일 때 발화하지 않고 `P?` 로 가는가
2. **렌즈 불변량 (property test)** — 어떤 가중치 벡터로도 버킷과 `pending_escalations`
   가 바뀌지 않는다. 바뀌는 것은 **같은 버킷 안의 정렬뿐** (SPEC 11.3 문구 그대로)
3. **부록 E 종단 시나리오** — 정보가 늘면서 결론이 바뀌는 7단계를 재현

**근거** (사용자 결정): ADR-006 에서 적용성만 객관적 골드셋이 가능하다고 못박았다.
우선순위의 정답은 현장 전문가 합의에서만 나오는데(기획서 18.1) **라벨링할 전문가가
없다.** 없는 근거로 정확도를 주장하는 것이 최악의 선택지다.

**논문·발표에서 지킬 선**: "적용성 판정은 권고문에서 파생된 골드셋으로 검증했고,
우선순위는 규칙의 일관성과 설명 가능성을 보인 것이지 정확도를 주장하지 않는다."
이 문장을 빼면 심사에서 정확히 여기가 뚫린다.

## ADR-009 · KEV 만 연동, EPSS 는 보류

**결정**: 슬라이스 2 는 **CISA KEV 만**. EPSS 는 슬라이스 2.5 로 미룬다.

**근거**: KEV 는 H01 이 직접 참조하므로 필수다. EPSS 는 표 13 이 "정렬 보조"로 규정한

적용성이 확정되기 전에 정렬 신호를 늘리는 것은 "심각도 높으니 조치"라는 기존 도구의
실패 모드에 가까워지는 방향이다.

### 검증 결과 (2026-09-09 실측)

`https://www.cisa.gov/sites/default/files/feeds/known_exploited_vulnerabilities.json`
— catalogVersion 2026.09.08, 1,699건, `vulnerabilities[].cveID`.

**KEV 는 OT 제품을 거의 다루지 않는다.** Siemens·Mitsubishi·Schneider·Rockwell·
Delta·Moxa 를 합쳐 1,699건 중 **4건**이다. 이것 자체가 제품 포지셔닝의 근거다 —
이 플랫폼의 가치는 "KEV 필터링"이 아니라 적용성과 도달성에 있다.

그럼에도 **H01 은 실데이터로 발화한다**:

> `SSA-019113`(SIMATIC S7-1500 MFP)의 431개 CVE 중 `CVE-2026-31431`(Linux Kernel)이
> KEV 에 있다. PLC **펌웨어**가 아니라 PLC 안의 **Linux 서브시스템**에서 걸린다.

표 15 가 왜 자산과 부품을 분리하라고 하는지를 그대로 보여주는 사례다. 부품을 분리하지
않았다면 이 KEV 히트는 보이지 않는다.

**스냅샷 규칙**: KEV 는 `data/kev/<snapshot-date>/` 에 원문 그대로 저장하고 sha256 과
스냅샷 날짜를 `input_hash` 에 넣는다. 오늘의 KEV 로 과거 판정을 재현하면 안 된다.

## ADR-012 · 충돌은 '증거 비교 데이터 경로'로 구현, 모순 탐색은 보너스

## ADR-013 · 합성 토폴로지는 Purdue + IEC 62443 참조 구조를 따른다

**결정** (사용자): 토폴로지를 임의로 만들지 않고 **Purdue Level 0~5 + IEC 62443
Zone/Conduit** 구조를 따른다. 픽스처 파일에 근거를 명시한다.

**근거**: 슬라이스 3 은 앞선 둘과 구조가 다르다.

| 슬라이스 | 정답의 출처 |
|---|---|
| 1 적용성 | 권고문에서 파생 — **객관적** |
| 2 우선순위 | 없음 (전문가 부재) → 정확도 주장 안 함 (ADR-008) |
| 3 경로 | **없음 — 토폴로지가 100% 합성** |

ADR-006 이 이미 못박았다: 도달성·공정 영향은 현장 증거로만 얻을 수 있고 외부 소스로
대체 불가다. 임의 합성은 "왜 이 구조냐"에 답할 수 없다. 표준 참조 구조를 따르면
적어도 **구조의 출처**는 댈 수 있다. 기획서 부록 G 가 이미 R2(NIST SP 800-82 Rev.3),
R14(ISA/IEC 62443)를 인용하고 있다.

**정직하게 남길 한계**: 800-82 는 PDF 도면이고 62443 은 유료 표준이다. 따라서 이것은
**"표준의 계층 구조를 따른 합성"이지 "공개 데이터셋"이 아니다.** 발표에서 이 구분을
흐리면 안 된다. 픽스처의 `provenance` 블록에 `"synthetic": true` 를 명시한다.

## ADR-014 · 도달성은 관측 엣지로만 확정한다

**결정** (사용자, 안 A): 경로의 **모든 엣지가 관측(observed)** 일 때만 도달성이 TRUE 다.
추론(inferred) 엣지가 하나라도 섞이면 UNKNOWN 을 유지한다.

**근거**: SPEC 10.1 — "확인된 통신은 실선, 규칙 추론은 점선, 정보 부족은 회색으로
표시하고 **추론 경로를 자동으로 확정하지 않는다**". 설계 원칙 P1(확정과 추론을 섞지
않음)과 슬라이스 1~2 에서 지켜온 선이 같다. 추론으로 도달성을 확정하면 그것이 곧
경로판 false safe 의 반대편 — 거짓 확신(R06)이다.

### 세 평가자의 반환 규칙

`유효 경로` · `중요 자산 도달` · `외부 상위 Zone 도달` 은 모두 이 형태를 따른다:

| 상황 | 반환 |
|---|---|
| 진입점→대상 경로가 있고 **모든 엣지가 observed** | `TRUE` |
| 경로는 있으나 inferred/unknown 엣지가 섞임 | `UNKNOWN` (막는 엣지를 이름으로 지목) |
| 그래프에 자산이 있고 **어떤 상태의 경로도 없음** | `FALSE` |
| 그래프에 자산이 아예 없음 | `UNKNOWN` |

마지막 줄이 중요하다 — 토폴로지에 없는 자산을 "도달 불가"로 답하면 false safe 다.

## ADR-015 · ATT&CK ICS 는 엣지 타입에만, 출처를 명시해서

**결정** (안 B): ATT&CK ICS STIX 를 **버전 고정**해 로드하고, **엣지 타입 → 기법**
매핑만 붙인다. **CVE → 기법 매핑은 하지 않는다.**

**근거**: SPEC 10.1 — "CVE 에서 기법으로의 연결은 **출처가 있는 매핑과 내부 추론을

엣지 타입→기법은 **경로 구조에서 직접 도출**되므로 근거를 댈 수 있다. 그래도 내부
매핑임을 숨기지 않고 각 항목에 `provenance: "internal:edge_type"` 을 붙인다.

**검증** (2026-09-09): `github.com/mitre-attack/attack-stix-data` → `ics-attack/
ics-attack-19.2.json` (2026-08-05 릴리스). 표 14 의 "버전 고정" 요구를 만족한다.

## ADR-016 · 시각화는 결정적 SVG, JS 라이브러리 없음

**결정** (안 A 에서 refinement): 정적 HTML 을 생성하되 **Cytoscape.js 를 쓰지 않는다.**
Purdue 레벨을 행으로 놓는 **직접 작성한 결정적 SVG** 로 그린다. JS 코드 0줄.

**변경 사유**: 원래 "Cytoscape.js 인라인"을 추천했으나 설계 중에 문제를 발견했다 —
**force-directed 레이아웃은 비결정적이다.** 실행할 때마다 좌표가 달라지면 두 슬라이스
동안 지켜온 바이트 동일 게이트가 깨진다.

그리고 Purdue 모델은 **본래 계층 구조**라 레이어드 레이아웃이 자연스럽다. 레벨=행,
같은 레벨 안에서는 zone → asset_id 순 정렬이면 좌표가 완전히 결정적이다. 라이브러리가
오히려 나쁜 선택이었다.

부수 효과로 폐쇄망 요구(NFR-OFF-001)도 깨끗해진다 — CDN 도, 700KB 인라인도 없다.
상호작용은 hover `<title>` 툴팁까지만.

**표시 규칙 고정** (SPEC 10.1, 그림 5): 확인=실선 · 추론=점선 · 정보 부족=회색.
색 이외의 수단으로도 구분한다 (NFR-A11Y-001).

### 정정 (산출물 단계) — "JS 0줄" 은 과한 조문이었다

원래 결정을 "JS 0줄"로 적었는데, **실제 제약은 두 가지**였다:
**비결정적 레이아웃 금지**(바이트 동일 게이트)와 **외부 자원 금지**(폐쇄망).
인라인 JS 로 *표시*를 바꾸는 것은 둘 중 어느 것도 어기지 않는다.

`scripts/build_ui.py` 가 만드는 대화형 UI 는:
- 조합 288개(자산 × 권고 × as_of × 토폴로지 유무)를 **파이썬이 미리 계산**해 JSON 으로 심는다.
  계산은 여전히 결정적 엔진이 하고, JS 는 고르고 정렬만 한다.
- 레이아웃은 그대로 Purdue 레벨=행 SVG — force-directed 를 쓰지 않는다.
- 외부 자원 0개. 파일 하나만 복사하면 폐쇄망에서 그대로 뜬다.
- 두 번 생성하면 **바이트 동일**하다.

**예외 하나**: 렌즈 가중치만 브라우저에서 다시 계산한다. 가중치를 아무리 움직여도
**버킷이 절대 안 움직인다**는 불변량을 눈으로 보여주기 위해서다 —
`scripts/check_ui.py` 가 Playwright 로 그 성질을 실제 브라우저에서 검증한다.

> **후속**: ADR-028 에서 웹앱에 Cytoscape.js 를 들였다. 이 결정을 뒤집은 것이
> 아니다 — 결정적 SVG 는 그대로 남아 바이트 동일 게이트를 계속 지키고,
> Cytoscape 화면은 게이트 대상이 아닌 **탐색용**이다.

## ADR-017 · 차단 후보는 점수가 아니라 두 개의 정수로 제시한다

**결정**: 가상 차단 시뮬레이션(FR-PATH-003)을 포함한다. 각 후보 엣지에 대해
**`paths_cut`(끊기는 공격 경로 수)** 와 **`legitimate_flows_broken`(끊기는 정상 통신 수)**
두 정수를 제시하고, `paths_cut DESC, legitimate_flows_broken ASC` 로 정렬한다.

**근거**: 이것이 없으면 경로 엔진은 그냥 그래프 탐색이다. 표 44 의 차별화 축
"현실적 차단 지점"이 여기서 나오고, 패치 불가 EOL 자산에 대한 유일한 답이기도 하다.

**점수를 만들지 않는 이유**: 설계 원칙 P6 — "점수보다 결론을 바꾼 조건과 누락 정보와
대안 조치를 먼저 제시". 가중 합산 점수 하나는 "왜 이 차단점인가"에 답하지 못한다.
정수 두 개는 답한다: "경로 4개를 끊고 정상 통신 1개를 끊습니다."

## 슬라이스 3 의 검증 축 — 정확도는 주장하지 않는다

골드셋이 없으므로(ADR-013) 검증은 세 가지로 한정한다. ADR-008 과 같은 선이다.

1. **그래프 알고리즘 단위 검증** — 전제조건 상태 전이·홉 제한·능력 격자가 정확한가 (객관적)
2. **불변량** — 추론 엣지가 확정으로 승격되지 않는다 / 그래프에 없는 자산을 도달 불가로
   답하지 않는다 / 차단 후보가 끊는 정상 통신이 반드시 표시된다
3. **시나리오** — 관측이 늘면서 `P?` 가 확정 등급으로 움직이는 과정

**경로 탐지 정확도는 주장하지 않는다.** 논문·발표에서 이 선을 넘지 않는다.

### 구현 중 확인된 것

**ADR-002(Neo4j 미도입)가 실측으로 확정되었다.** `scripts/bench_paths.py`:

| 엣지 | 경로 | p95 |
|---|---|---|
| 10,000 | 15 | 0.03s |
| 50,000 | 75 | 0.27s |
| 100,000 | 150 | **0.63s** |

NFR-PERF-002 기준(5홉/10만 엣지/p95 5초)을 여유 있게 만족한다. ADR-002 의 재검토
트리거는 발동하지 않았다.

다만 첫 구현은 이 벤치마크에서 **멈췄다** — `out_edges` 가 매 호출마다 엣지 전체를
선형 탐색했기 때문이다. 인접 인덱스(엣지 key 순 정렬로 결정성 유지)와 경로 수 상한
(`MAX_PATHS=500`, 경로 열거는 지수적이다)을 넣어 해결했다. 벤치마크를 돌리지 않았으면
발견하지 못했을 결함이다.

**ATT&CK 버전 고정이 왜 필요한지도 실물로 확인됐다.** v19 에서 ICS 기법 체계가 재편되어
`T0855`(Unauthorized Command Message)가 revoked 되고 `T1692.001` 로 대체되었다.
ID 를 고정 문자열로 박아둔 채 검증하지 않으면 매핑이 **조용히 비어버린다**.
`verify_mapping()` 과 그 테스트가 이것을 막는다.

## ADR-018 · 번들 서명은 Ed25519, `sig_alg` 로 일방통행 문을 피한다

**결정** (사용자): Ed25519 (`cryptography`). 매니페스트에 `sig_alg` 필드를 두어
나중에 GPG 등을 추가해도 **기존 번들이 계속 검증**되게 한다.

| 안 | 의존성 | R09(공급망) 방어 |
|---|---|---|
| **A Ed25519** | 첫 런타임 의존성 | ✅ 공개키 서명. 폐쇄망엔 공개키만 반입 |
| B GPG 외부 호출 | gnupg 프로세스 | ✅ 하지만 테스트가 환경에 묶인다 |
| C HMAC-SHA256 | 0 | ❌ **대칭키** — 검증하려면 위조도 가능한 비밀이 필요 |

C 는 "서명"이 아니라 "체크섬"이다. 검증자가 서명 비밀을 알아야 하므로 배포처가
늘수록 위조 가능성이 늘고, R09 가 겨누는 공급망 위협에 답하지 못한다.

**정직하게 남길 대가**: `cryptography` 는 순수 파이썬이 아니라 **컴파일된 확장**을
포함한다. 지금까지 폐쇄망 반입은 `.py` 복사였지만, 이제 플랫폼·파이썬 버전에 맞는
wheel 을 함께 반입해야 한다 (NFR-OFF-001 의 실제 부담). 그리고 R09 가 겨누는 신뢰
대상이 하나 늘어난다 — 의존성 자체를 고정하고 감사해야 한다.

**검증 순서 — 세 번째가 흔히 빠진다**:
1. 서명 (매니페스트 정규 바이트, `input_hash` 와 같은 정규화)
2. 파일별 sha256
3. **매니페스트에 없는 멤버가 zip 에 있는지** ← 서명을 위조 못 해도 파일은 끼워넣을 수 있다

번들은 결정적이다 — zip mtime 을 1980-01-01 로 고정해 **바이트 동일 게이트**를 적용한다.

## ADR-019 · 감사의 actor 는 '주장' 이지 사실이 아니다

**결정**: `--actor` 로 받되 `actor_authenticated` 를 **별도 컬럼**으로 함께 기록한다.
슬라이스 4 에는 인증이 없으므로 항상 `0` 이다.

**근거**: FR-GOV-002 는 "누가"를 요구하지만 이 시스템엔 아직 사용자 개념이 없다
(OIDC/RBAC 는 슬라이스 5+). 인증되지 않은 주장을 인증된 사실처럼 기록하면 **감사
로그가 감사 가치를 잃는다** — 슬라이스 1~3 에서 "확정과 추론을 섞지 않는다"로
지켜온 것과 정확히 같은 문제다.

슬라이스 5 에서 인증이 붙으면 그 필드가 `1` 이 되고, 과거 기록은 여전히 "그때는
인증이 없었다"를 정확히 말한다. 소급해서 고치지 않는다.

감사 테이블도 append-only 트리거로 UPDATE/DELETE 를 막는다 (NFR-AUD-001).
`correlation_id` 에 `input_hash`·`priority_input_hash`·매니페스트 해시를 넣어
감사자가 이벤트를 **정확히 그 판정**에 연결할 수 있게 한다.

## ADR-020 · 적대적 입력 방어를 먼저, 그리고 여기서는 정확도를 주장한다

**결정**: `otai/safeio.py` 를 신뢰할 수 없는 바이트를 다루는 **유일한 모듈**로 두고,
번들·CSV 보다 **먼저** 구현한다. 다른 모듈에서 `zipfile.extractall`·`json.load`·
`csv.reader` 를 직접 부르지 않는다.

**순서의 이유**: 번들의 `apply` 경로가 곧 신뢰할 수 없는 파일 경로다. `safe_extract`
가 없는 상태로 bundle.py 를 쓰면 `extractall` 을 쓰게 되고 다시 고쳐야 한다.

### 슬라이스 4 는 정확도를 주장할 수 있다

앞선 두 슬라이스와 결정적으로 다른 점이다.

| 슬라이스 | 정확도 주장 | 이유 |
|---|---|---|
| 2 우선순위 | ❌ | 전문가 합의 골드셋 없음 (ADR-008) |
| 3 경로 | ❌ | 토폴로지가 100% 합성 (ADR-013) |
| **4 적대 입력** | **✅** | **"거부되어야 한다"의 정답이 객관적** |

인수 기준 = 아래가 전부 거부되는 것. `tests/test_adversarial.py` 가 인수표다.

경로순회(`../`) · 중간 경유 zip slip · 절대경로 · 드라이브 문자 · 역슬래시 주입 ·
심볼릭 링크 멤버 · 압축폭탄 · 총량 초과 · 멤버 수 초과 · 과중첩 JSON · 거대 JSON ·
CSV 수식 인젝션(`= + - @ \t \r`) · 서명 위조 · 파일 변조 · **미신고 멤버 밀반입**

### 구현 중 확인된 것

**과중첩 JSON 은 파싱 후 검사로는 못 막는다.** `json.loads` 자체가 깊이 제한이 없어
`RecursionError` 로 죽는다 — 파싱한 뒤 깊이를 재는 것은 이미 늦다. 파싱 **전에**
괄호 깊이를 세는 `_textual_depth` 를 넣고 `RecursionError` 를 최후 방어선으로 뒀다.

**zipfile 은 플랫폼별로 멤버 이름을 정규화한다** (윈도우에서 역슬래시 → `/`).
따라서 실제 아카이브로는 만들 수 없는 공격 이름이 있다. 검사 자체는 반드시 존재해야
하므로 이름 단위 검증(`check_member_name`)을 아카이브 단위 테스트와 분리했다.

## ADR-021 · 예외는 강제규칙을 뚫지 못한다

**결정**: 승인된 위험 수용(FR-ACT-001)을 구현하되, **강제규칙이 발화한 항목에는
적용되지 않는다.** 렌즈에 적용한 것과 같은 보호다 (표 23: "사용자 가중치로 하향 불가").

**근거**: 예외는 규칙이 발화하지 않은 항목의 잔여 위험을 사람이 책임지고 수용하는
장치이지, **안전 하한을 뚫는 수단이 아니다.** 뚫을 수 있으면 강제규칙이 강제가 아니다.

예외에는 승인자·사유·만료일이 필수이고, 만료 후에는 항목이 계산된 버킷으로 돌아온다.
예외 테이블도 append-only 다 — 철회하려면 만료된 새 예외를 추가한다.

## ADR-022 · NVD·EPSS 를 의도적으로 구현하지 않는다

**결정** (사용자): 표 35 Must 의 "CVE NVD KEV EPSS CSAF" 중 **CSAF·KEV 만** 구현하고
NVD·EPSS 는 **의도적으로 남긴다.** Must 를 형식적으로 채우지 않는다.

**근거**
- **EPSS** — 표 13 이 "정렬 보조"로 규정하고 "OT 특화 확률로 오인 금지"라고 명시까지
  했다. 적용성이 확정되기 전에 정렬 신호를 늘리는 것은 "심각도 높으니 조치"라는
  기존 도구의 실패 모드에 가까워지는 방향이다 (ADR-009 의 근거가 그대로 유효).
- **NVD** — 표 13 은 CVE 기본 기록의 1차 권위를 **CNA** 로, NVD 를 "보강"으로 둔다.
  CSAF 가 이미 그 필드를 채우고 있어 중복이다.

슬라이스 2 에서 KEV 가 1,699건 중 주요 ICS 벤더를 4건만 다룬다는 것을 확인한 것과
같은 맥락이다 — **미구현을 명시하는 편이 형식적 충족보다 정직하다.**

## ADR-023 · `vers:all/*` 는 와일드카드다 — 슬라이스 1 회수율 교정

**결정**: `vers:all/*`(모든 버전 영향)를 파싱 실패가 아니라 **와일드카드**로 인식한다.
`RULE_VERSION` 을 `applicability/1.1.0` 으로 올린다.

**발견 경위**: 소스 비교를 붙이려고 `SSA-452276` 을 열었더니 157개 product 중
**23개(15%)** 가 `vers:all/*` 를 쓰고 있었다. 기존 파서는 이를 파싱 실패로 처리해
`UNKNOWN` 을 냈다.

**왜 중요한가**: false safe 는 **아니다** (UNKNOWN 은 '안전' 이 아니다). 하지만 적용
대상을 놓치는 것이므로 표 39 의 **후보 Recall ≥98%** 를 깎는다. 두 오류는 성격이
다르고 둘 다 인수 기준에 있다.

**단, 버전을 아는 경우에만 확정한다.** "모든 버전이 영향" 이어도 자산의 버전을 모르면
`UNKNOWN` 이다 — 그 자산은 식별 경로를 통해 `affected_likely` 로 가야지 자동으로
확정되면 안 된다.

판정이 바뀌는 변경이므로 규칙 버전을 올려 **해시가 함께 달라지게** 했다.

## ADR-024 · 소스 권위는 발행처 표로 판단한다 — 그리고 흔한 것은 모순이 아니라 일치다

**결정**: `publisher.category` 를 신뢰하지 않고 **알려진 발행처 표**로 역할을 판단한다.
표에 없을 때만 선언 값을 쓰고, **어느 쪽을 썼는지도 함께 기록**한다.

### 실측 근거 1 — `category` 는 일관되지 않는다

같은 CISA 가 파일마다 다르게 선언한다:

| 파일 | 선언 category | 실제 역할 |
|---|---|---|
| `icsa-26-036-02` | `coordinator` | coordinator |
| `icsa-26-071-04` | **`other`** | coordinator |

R04(벤더 권고 비정형)가 본문이 아니라 **메타데이터에서** 나타난 사례다. 선언 값을
그대로 믿었다면 같은 기관이 파일마다 다른 권위를 갖게 된다.

### 실측 근거 2 — CISA 는 Siemens 문서를 재발행한다

`ICSA-26-071-04` ↔ `SSA-452276` (CVE-2025-40943) 비교 결과:

| 비교 항목 | 결과 |
|---|---|
| product 수 | 157 vs 157 |
| 버전 범위 | **완전 일치** |
| CVSS 벡터 | **완전 일치** |
| 주문번호 | 135개 **전부 일치** |
| 충돌 | **0건** |
| 다른 것 | advisory_id · 발행처 · 개정(6 vs 4) · 시점(05-14 vs 05-12) |

ADR-005 에 "겹치는 구간이 곧 데모"라고 쓴 것은 절반만 맞았고, ADR-012 에서 "재발행
구조라 모순이 적을 가능성" 이라고 한 예상이 맞았다.

**그래도 기능은 성립한다.** FR-SRC-005 는 "모순 탐지"가 아니라 **"자동 덮어쓰기
금지"** 다. 구현한 것은:
- 모든 주장 보존 (`FieldView.claims`), 현재 값은 **계산된 뷰**
- 필드별 권위 (표 13) — 제품 영향·버전 범위는 벤더가, CVSS 는 CNA가 있으면 CNA가
- 일치할 때는 `corroborated_by` 로 **교차 확인**을 보여줌
- 시점·개정 차이는 `PROVENANCE_FIELDS` — 충돌이 아니라 출처 정보

**연결은 CVE 교집합으로 한다.** 제품 겹침은 근거가 약하고 참조 문자열은 형식이
보장되지 않는다. CVE 는 두 소스가 반드시 공유하는 유일한 식별자다.

**양쪽 원문 해시를 모두 들고 다닌다** — 한쪽만 기록하면 다른 쪽이 개정돼도 해시가
그대로여서 재현성이 깨진다.

### H05 가 처음으로 실제 트리거를 얻었다

`H05`(소스 충돌 + 안전 영향)는 슬라이스 2~4 동안 **발화 경로가 없던 유일한 강제규칙**
이었다. 소스 비교가 `source_conflict` 신호를 넘기면서 비로소 발화한다.

## ADR-025 · 병합·분리는 과거를 다시 쓰지 않고 계보로 연결한다

**결정** (사용자, 안 C): 자산 병합 시 **과거 판정 행을 그대로 둔다.** `identity_link`
테이블에 링크를 추가하고, 조회할 때 계보를 합쳐 보여준다.

| 안 | 문제 |
|---|---|
| A 과거 보존 + 이후만 새 id | 이력이 끊긴다 |
| B 과거를 새 id 로 재계산 | **append-only 불변 규칙을 정면 위반** (과거를 다시 씀) |
| **C 보존 + 링크로 연결** | 조회가 복잡하지만 두 원칙을 다 지킨다 |

`lineage(asset_id, as_of)` 는 **as_of 를 존중한다** — 병합 이전 시점으로 조회하면
계보는 자기 자신뿐이다. 그래야 "그때 우리가 알던 것"이 재현된다.

승인자는 필수이지만 **인증되지 않은 주장**이다 (`actor_authenticated=0`, ADR-019).
`identity_link` 도 append-only 트리거로 보호한다 — 되돌리려면 반대 방향 링크를 추가한다.

## ADR-026 · 정책은 데이터, 규칙 DSL 은 만들지 않는다

**결정**: 이미 매개변수인 값들(신선도·CVSS 임계·홉 수·기본 버킷·강제규칙 floor·렌즈)
을 `Policy` 파일로 빼고, **내용 해시로 버전**을 만든다. 규칙의 *구조*는 코드가,
*임계값*은 정책이 쥔다.

```
POLICY_VERSION = "policy/<sha256[:12]>"
```

**DSL 을 만들지 않는 이유**: 규칙 해석기를 쓰면 그 해석기 자체가 검증 대상이 되고,
"결정적 규칙 모듈"이라는 성질이 흐려진다. 임계값 외부화만으로 FR-GOV-001 의 요구
(버전 관리·승인·롤백·영향 미리보기)를 전부 만족한다.

- **승인·롤백**: 번들의 `current` 포인터 패턴 재사용 (ADR-018)
- **영향 미리보기**: 같은 입력을 정책 A·B 로 돌려 뒤집히는 판정을 diff
- **영향 범위 좁히기** (결정 2C): 바뀐 필드 → 건드리는 평가자를 역추적.
  메타데이터(작성자·승인자·근거)만 바뀌면 평가자 목록이 비고 미리보기도 빈다 —
  단, **버전은 달라진다** (내용이 바뀌었으므로)
- **FR-RISK-003 렌즈 저장·미리보기는 정책의 부분집합**이다. 렌즈는
  `Policy.lens_presets` 이고, 버킷 불변 성질은 기존 property test 가 계속 지킨다

**정책이 강제규칙의 floor 는 바꿀 수 있어도 발화 자체는 막지 못한다.** 테스트가 이를
고정한다 — 그렇지 않으면 정책 파일이 안전 하한을 우회하는 통로가 된다.

## ADR-027 · PostgreSQL 을 기본 저장소로, SQLite 는 명시적 선택으로

**결정**: ADR-003 의 전환 조건(ADR-011 로 "동시 쓰기 주체 2 이상")이 충족되었다.
웹앱은 ASGI 스레드풀에서 여러 요청이 동시에 쓴다. `otai web` 의 기본 `--db` 는
`postgresql://otai:otai@127.0.0.1:5433/otai` 이고, SQLite 는 파일 경로를 명시할 때만 쓴다.

두 엔진은 `otai/db.py` 의 얇은 계층(`Conn`)으로 공존한다. `?` 자리표시자 하나로 쓰고,
`translate_ddl()` 이 DDL 을 옮긴다. `Repo` 와 `Store` 둘 다 이 계층 위에 있다.

**옮기다 빠뜨리면 조용히 사라지는 것이 하나 있다 — append-only 트리거다.**
SQLite 는 `SELECT RAISE(ABORT, ...)`, PostgreSQL 은 트리거 함수의 `RAISE EXCEPTION`
이라 문법이 전혀 다르다. 빠뜨려도 테이블은 만들어지고 INSERT 도 되고 화면도 정상이다.
UPDATE/DELETE 만 조용히 통과한다 — 불변 규칙 3 이 주석으로 강등되는 것이다.
그래서 `tests/test_postgres_backend.py` 는 "트리거가 옮겨졌는가"가 아니라
**"5개 테이블 전부에서 UPDATE 와 DELETE 가 실제로 거부되는가"** 를 본다.

**연결 실패 시 SQLite 로 자동 폴백하지 않는다.** 폴백하면 감사 기록이 두 저장소로
갈라지고 아무도 눈치채지 못한다 — 계보 완전성(불변 규칙 5)의 구멍이다. `otai web` 은
크게 실패하고 `pg_ctl` 기동 명령과 `--db` 우회 방법을 함께 출력한다.

**PostgreSQL 에서는 감사 저장소를 분리하지 않는다** (`audit_dsn()`). 테이블 이름이
겹치지 않고(`asset_row/zone` vs `assertion/decision/event/exception/identity_link`),
한 트랜잭션 경계 안에 두는 편이 계보에 유리하다. SQLite 일 때만 파일을 나눈다.

**DSN 은 문자열로 다룬다.** `--db` 를 `type=Path` 로 두면 Windows 에서
`postgresql://otai:otai@127.0.0.1:5433/otai` 가 `postgresql:\otai:otai@...\otai` 로
바뀌어 그 이름의 SQLite 파일이 만들어진다. 실측으로 확인한 함정이다.

**폐쇄망 영향 없음**: PostgreSQL 은 온프레미스에 함께 배포된다. `otai decide` 등
CLI 경로는 여전히 SQLite 기본이라 진입 장벽(ADR-003 의 원래 근거)도 유지된다.

## ADR-028 · 웹 UI 는 Vite + TypeScript 로 빌드하고, 경로는 해시로 쓴다

**결정**: 표 27 의 "React + TypeScript + Cytoscape.js" 를 문자 그대로 구현한다.
`frontend/` 에서 Vite 가 `web/dist` 로 빌드하고 FastAPI 가 `/ui` 에 마운트한다.
`npm run build` 는 `tsc --noEmit` 을 먼저 돌려 타입 오류를 빌드 실패로 만든다.

**ADR-016 과 충돌하지 않는다.** ADR-016 이 지킨 제약은 두 개였다 —
비결정적 레이아웃 금지(바이트 동일 게이트)와 외부 자원 금지(폐쇄망).
결정적 SVG(`otai render`, `scripts/build_ui.py`)는 **그대로 남아 있고** 그 게이트를
계속 지킨다. 웹앱의 Cytoscape 화면은 **탐색용이지 산출물이 아니다** — 바이트 동일
게이트의 대상이 아니고, 대상인 산출물은 여전히 파이썬이 그린다.
외부 자원은 0개다: 번들은 전부 로컬에서 만들어 함께 배포하고, `scripts/check_web.py`
가 실제 브라우저에서 **출처(origin) 기준으로** 확인한다.

**경로는 해시 라우팅**(`/ui/#/asset/plc-line3-01`)이다. 서버에 catch-all 이 필요 없어
`StaticFiles` 마운트 하나로 끝나고, 딥링크를 새로고침해도 404 가 나지 않으며,
정적 파일만 복사해도 폐쇄망에서 그대로 뜬다.

**UMD 판을 지우지 않고 `/legacy` 로 남긴다.** `web/dist` 가 없으면 `/` 가 UMD 판을
서빙한다 — node 없는 환경에서도 UI 가 뜬다는 폐쇄망 안전망이다. 다만
`scripts/check_web.py` 는 어느 쪽을 검사 중인지 첫 줄에 찍는다. 빌드가 없는데 옛 화면을
조용히 검사하고 통과하면 검증이 거짓말이 된다.

## ADR-029 · 화면은 '야간 관제실', 통제 어휘는 뜻으로 보여준다

**결정**: ISA-101 종이 팔레트(저채도 크림 배경 · 바탕체 serif · 고정폭 데이터)를 버리고
**어두운 관제 화면**으로 간다. 사용자가 세 번 "구식"이라고 지적했고, 그 지적이 맞았다 —
바탕체는 한국어에서 관공서 문서를 그대로 연상시키고, 12.5px 본문에 모든 칸이 1px 테두리인
표는 2005년 사내 시스템의 외형이다.

- **바탕**: 순수 검정이 아닌 청색 편향 딥슬레이트(`#0B0F14`). 어두운 방에서 순수 검정 위의
  흰 글씨는 잔상이 남는다.
- **상태색은 형광 한 색이 아니라 확신도 3축**: 해당함(적) · 판단 보류(앰버) · 해당 없음(청록).
  색만으로 구분하지 않는다 — 글리프(`● ◐ ○`)와 등급 글자가 항상 함께 간다 (NFR-A11Y-001).
  `scripts/check_web.py` 가 실제 브라우저에서 본문 명암비 4.5:1 을 계산해 확인한다.
- **글꼴**: Pretendard Variable 을 **로컬에 반입**한다 (OFL 1.1, 재배포 허용).
  CDN 을 부르지 않으므로 폐쇄망 요구가 유지된다.

**길 안내가 시그니처다.** "화면 안에서 길을 잃는다"가 디자인 불만과 함께 나온 지적이었다.
- 좌측 레일을 **하는 일**로 묶는다: 작업 / 파고들기 / 무엇을 믿고 있나.
- 할 일 맨 위에 **"지금 이것 하나"** 초점 카드를 둔다. 여기에는 **조치할 수 있는 항목만**
  온다. `P?` 는 조치가 아니라 질문이므로 아래 '확인하면 등급이 오르는 것' 으로 간다 —
  막힌 것을 하라고 시키면 안 된다.
- 공격 경로는 **Purdue 레벨 = 행**으로 놓는다. 이 도메인은 원래 층 구조이고 공격은
  위(기업망)에서 아래(현장)로 내려온다. 층 이름은 노드의 실제 렌더 좌표에 붙인다.

**통제 어휘는 없애지 않고 옮긴다** (`frontend/src/terms.ts`). 표 10 의 한국어 문구
(`적용 확인` 등)는 기획서가 고정한 값이라 그대로 둔다. 화면에서 빼는 것은 그 옆에
따라다니던 **영문 코드**다 — `affected_confirmed`, `H02`, `Composite` 는 '자세히' 안으로
들어가고, 본문에는 뜻과 근거를 문장으로 쓴다.

**`no_known_match` 의 평이한 문구를 줄이지 말 것**: "지금 가진 범위에서 못 찾았습니다 /
안전하다는 뜻이 아닙니다." 짧게 만들면 그 순간 false safe 다 (불변 규칙 1).

### 함정 하나 — cytoscape `layout: 'preset'`

Purdue 좌표를 `layout: {name:'preset'}` 으로 주면 **노드 15개 중 3개만 칠해진다**
(cytoscape 3.30, `width: 'label'` 과 맞물리는 문제). 모델은 멀쩡하다 — `cy.nodes().length`,
`renderedPosition()`, `boundingBox()`, 계산된 스타일이 전부 정상이라 진단이 오래 걸린다.
**`breadthfirst` 로 한 번 그린 뒤 좌표만 옮긴다.**

그리고 이 버그를 **캔버스 전체의 칠해진 픽셀 비율** 검사가 통과시켰다. 지금은
`drawn_ratio()` 가 **노드마다 그 자리를 직접 찍어본다** — 통과하는데 화면이 깨져 있으면
검사가 아니라 소음이다.

## ADR-030 · 규모는 사전 필터로 감당한다 — 그리고 그 필터를 전수로 증명한다

**결정**: 권고문 1,303건 · 자산 1,359개로 규모를 키우면 대조해야 할 쌍이 **177만**이 된다.
쌍당 0.31ms 라 전부 판정하면 9분이다. `otai/identity.py` 의 `could_match()` 가
가망 없는 쌍을 먼저 걸러낸다 — 실측 **97.3% 감소**(177만 → 4.8만), 전수 판정 18초.

**필터는 `_match_one()` 의 필요조건이다.** 매칭이 성립하려면 넷 중 하나여야 한다:
주문번호가 `model_numbers` 에 있거나(Exact), 벤더 토큰이 부분집합 관계이거나
(Deterministic·Composite — 교집합이 비지 않음), 제품명 토큰 중첩이 0.6 이상이거나
(Fuzzy — 역시 교집합이 비지 않음). 따라서 **주문번호 불일치 + 토큰 교집합 공집합**이면
어떤 제품과도 일치하지 않고, `decide_applicability` 3단계에서 `no_known_match` 가 확정된다.
그래서 같은 파일에 둔다 — 매칭 규칙을 고치면 필터도 같이 고쳐야 한다.

**논증만으로는 부족하다.** 이 필터가 틀리면 그게 곧 false safe 다 — 영향받는 자산이
화면에서 통째로 사라지고 아무도 눈치채지 못한다. `tests/test_prefilter.py` 가
**177만 쌍 전부**에 대해 "건너뛴 쌍의 실제 판정이 `no_known_match` 인가"를 확인한다
(`-m slow`, 약 9분). 실측 위반 **0건**.

**식별 재료가 없는 자산은 건너뛰지 않는다.** 그쪽 결론은 `no_known_match` 가 아니라
`insufficient_information` 이고, 그것은 '해당 없음' 이 아니라 '판단 보류' 다.

**행동 큐는 시작할 때 배경에서 한 번 전수 계산한다.** 요청마다 돌리면 18초가 걸린다.
관점(lens)과 경로 반영만 요청 때 다시 계산한다 — 그 둘은 값이 싸고 요청마다 달라진다.
운영 콘솔이 전수 계산의 상태와 숫자를 보여준다.

**화면은 큰 수를 '안전' 으로 읽히게 두지 않는다.** "177만 쌍 중 172만 쌍 대상 아님" 은
자칫 안심으로 읽힌다. 그래서 자산 상세와 할 일 화면 모두에 **"대상이 아니라는 것은
안전하다는 뜻이 아닙니다"** 를 함께 쓴다 (부록 B).

### 합성 자산 (`fixtures/assets-scale/`)

`scripts/make_assets.py` 가 **실제 CSAF 제품 식별자에서** 자산을 파생한다 — 제조사·
제품명·버전 표기는 원문 그대로다. 지어낸 식별자로는 식별 사다리도 버전 비교기도
의미 있게 돌지 않는다. 제조사 366종 전부를 덮는다.

만들지 않는 것: **`network` 블록**(토폴로지에 없는 노드에 통신을 지어내면 도달성이
거짓이 된다 — ADR-013/014)과 대부분의 **공정 영향**. 새 자산의 도달성은 UNKNOWN 으로
남는 것이 정직하다.

**EOL 변형은 5개 중 1개만 만든다.** H04(지원 종료)는 적용성 전제 없이 발화하는
수명주기 규칙이라, 전 제품을 EOL 로 만들면 큐의 41%가 `P?` 가 됐다 — ADR-007 이
피하려던 바로 그 실패 모드다. 비율을 낮춰 28%로 내렸다.

모든 합성 자산은 본문에 `"synthetic": true` 를 싣고 자산 목록에 **합성** 배지가 붙는다.
실제 인벤토리로 오인하면 안 된다.

### 중복은 감추지 않고 묶는다

우선순위는 (자산 × 권고문) 쌍마다 평가되는데 막고 있는 전제는 자산의 성질인 경우가
많다 (도달성·수명주기). 그래서 규모가 커지면 같은 문장이 권고문 수만큼 반복된다 —
실측으로 383행이 322개의 서로 다른 사실이었다.

화면은 같은 자산·같은 미확인 전제·같은 floor 를 **한 줄로 묶고 "권고문 N건에서 동일"**
을 함께 적는다. 건수를 감추지 않으므로 정보가 사라지지 않고, 화면은 사실의 수를 보여준다.

### 남은 문제 (고치지 않았다)

**수명주기 발견이 권고문 수만큼 중복된다.** H04 는 자산 속성(EOL + 버전 미상)만 보는데
우선순위는 (자산 × 권고문) 쌍마다 평가된다. 그래서 EOL 자산 하나가 24건의 권고문과
매칭되면 같은 내용의 `P?` 가 24줄 뜬다. 표 4 가 `Lifecycle Finding` 을 `CVE` 와 다른
위험 객체로 분리한 이유가 이것인데, 지금 구현은 그 분리를 우선순위 단계까지 가져가지
않았다. 규모를 키우고서야 드러났다.

## ADR-031 · 막다른 길을 없애고, '모름' 을 한 낱말로 말한다

**결정**: 처음 온 사람이 걸리는 곳을 실측해서 고쳤다. 추측이 아니라 화면을 직접 세었다.

**막다른 길이 열 개 중 넷이었다.** 자산 상세·취약점·마인드맵·공격 경로를 메뉴에서
곧바로 누르면 `자산을 먼저 고르세요` 한 줄로 끝났다. 처음 온 사람에게 그건 벽이다.
이제 그 자리에 **자산 고르개**(검색 + 목록)가 뜬다. 빈 상태를 안내로 쓰는 관행이다 —
빈 화면에는 설명 대신 **거기서 할 수 있는 행동 하나**를 둔다.

**시작 안내는 별도 화면이 아니라 큐 위의 띠다.** 기본 홈은 여전히 행동 큐다 (위험 점수
대시보드가 아니라 '해야 할 일' 이 첫 화면이라는 것이 이 제품의 전제다). 안내는
"무엇을 할 수 있다" 가 아니라 **"지금 무엇이 준비됐고 다음에 무엇을 하면 되는지"** 를
말한다 — 셋업 체크리스트 관행. 한 번 닫으면 `localStorage` 에 기억하고 다시 뜨지 않는다.

**용어 사전을 그 안에 접어 넣었다.** 조치 등급·판정 상태·식별 완성도를 한자리에서
본다. 개별 화면의 설명을 없애지 않고 더한 것이다 — 처음에는 사전이 필요하고,
익숙해지면 화면 안 설명으로 충분하다.

**내비게이션 묶음 이름을 표준어로 바꿨다.** `파고들기` · `무엇을 믿고 있나` 는
시적이지만 처음 보는 사람이 `자산` · `취약점` · `보고서` 를 찾을 때 대응시키지 못한다.
`내 자산` · `분석` · `검증·운영` 으로 바꾸고 묶음마다 한 줄 설명을 붙였다.

### '모름' 은 한 낱말이다

같은 뜻이 화면마다 다르게 나왔다 — 장치 종류는 영문 `unknown`, 모델·구역은 `—`,
펌웨어는 `미상`. `—` 는 **'없음'** 으로 읽힌다. 이 제품에서 그 오독은 치명적이다:
불변 규칙 2 가 막는 것이 정확히 "모르는 값을 아는 값으로 붕괴시키는 것" 이다.

이제 전부 **미상**이다. 자산 목록 머리말이 그 뜻을 못박는다 — *"미상은 빈칸이 아니라
아직 모른다는 뜻입니다 — 없다는 뜻이 아닙니다."*

`asset_type` 은 **적용성·우선순위·식별 어디에도 쓰이지 않는다** (목록 필터와 라벨
전용). 그래서 `unknown` 이 많아도 판정은 조금도 나빠지지 않는다. 화면이 그 사실을
말한다 — 안 그러면 사용자가 데이터가 부실하다고 오해한다.

### 목록을 쏟아내는 화면 두 개

**출처 대조가 CVE 나열 12만 자였다.** 권고문 4건일 때는 `cves.join(', ')` 이 읽을
만했지만 1,303건이 되자 묶음 58개를 전부 펼치며 응답 411KB, 화면 125,809자가 됐다.
운영 콘솔의 '소스 상세' 도 권고문 id 1,303개를 한 칸에 넣고 있었다 (20,888자).

**목록(무엇이 있나)과 상세(그중 하나가 어떤가)를 나눴다.**
`/api/evidence/compare` 는 요약만 주고(22KB), `/api/evidence/compare/{id}` 가 하나를
펼친다. 화면은 왼쪽에서 고르고 오른쪽에서 본다. 정렬은 **충돌이 많은 순서** —
사람이 볼 이유가 거기 있다. 제품 대조도 값이 다른 것부터 싣는다.

운영 콘솔은 상태 카드 + 숫자 칩이 됐다. 소스별 건수와 살아 있는지, 전수 계산이
무엇을 몇 건 걸렀는지, 버전, 감사 이벤트. 목록은 어디에도 없다.

**관점 미리보기도 같은 병이었다.** 렌즈마다 전수 계산을 다시 돌아 36초가 걸렸다.
스윕 결과를 재사용하니 1.7초다 — 그리고 규모에서도 **등급이 바뀐 항목 0건**이
확인된다 (1,352건 중 796건 순서만 이동).

`scripts/check_web.py` 가 이제 **화면 분량 자체**를 검사한다 (`< 20,000자`).
숫자가 커졌을 때 조용히 무너지는 화면을 잡는 유일한 방법이다.

### 카탈로그 크기를 커버리지로 읽히게 두지 않는다

운영 콘솔이 `CISA KEV 1,699` · `ATT&CK ICS 97` 을 보여줬다. 맞는 수인데 사람은 그것을
**"우리가 이만큼 쓴다"** 로 읽는다. 실제로는:

| 소스 | 카탈로그 | 우리 범위에서 쓰이는 수 |
|---|---:|---|
| CISA KEV | 1,699 (CISA 가 확인한 악용 CVE 전체) | 우리 CVE 와 겹침 **53** → 실제 발견에 붙은 것 **20건** |
| ATT&CK ICS | 97 (번들 118개 중 폐기 21 제외) | 엣지 타입에 매핑한 기법 **3개** (T0836·T0843·T1692.001) |

이제 카드가 둘을 나눠 보여준다. **매핑을 늘려서 숫자를 맞추지 않았다** — 근거 없이
기법을 붙이는 것이 표 32 가 금지하는 바로 그것이다. 지금 엣지 타입은 3종
(`administers` · `can_reach_control` · `controls`)이고 각각에 검증된 기법 하나씩만 붙는다.
나머지 94개는 참조용으로 색인만 해 둔다.

**v19.2 고정은 의도다** (표 14). 릴리스마다 기법이 revoke 된다 — 실제로 v19 에서
T0855 가 사라져 매핑이 조용히 비었던 적이 있고, `verify_mapping()` 이 그걸 잡았다.
자동 최신 추종은 그 사고를 상시화한다.

### 생성기가 지어내던 것 하나

합성 자산에 `location.factory = "Factory-B"` 를 넣고 있었다. `network` 를 만들지 않는
것과 같은 이유로 **배치도 지어내면 안 된다** — 목록이 실제 인벤토리처럼 보이는 순간
거짓이 된다. 걷어냈다. 공장·구역은 이제 미상이다.

## ADR-048 · 실제 공개 캡처를 넣었다 — 그리고 합성으로는 안 보이던 것이 보였다

### 넣은 것

**4SICS 2015 GeekLounge 캡처** (Netresec 공개, CS3Sthlm 이 랩을 꾸렸다 —
https://www.netresec.com/?page=PCAP4SICS). 스웨덴 ICS 보안 컨퍼런스 전시 랩에서 뜬
트래픽이고, Siemens S7-1200 · DirectLogic 205 · Beckhoff CX1010 · RUGGEDCOM ·
Moxa · Allen-Bradley · Advantech 같은 **실제 장비**가 들어 있다.

1일차 25MB 를 `otai capture` 에 넣은 실측:

| | |
|---|---|
| 패킷 | 246,137개 · 관측 창 7시간 (2015-10-20 15:10 ~ 22:10 UTC) |
| 장비 | 10대 — `10.10.10.10` PLC(S7/102 수신) · `10.10.10.30` 워크스테이션(S7 발신) · `10.10.10.20` Siemens MAC · `192.168.88.61` Moxa MAC |
| 통신 | S7comm 94,859패킷 + 29,476패킷 · DNS · NTP · OpenVPN |
| 못 읽음 | IPv4 아님 6,870 · TCP/UDP 아님 2,740 (세어서 보고한다) |

**커밋한 것은 파생 토폴로지**(`fixtures/topology/4sics-geeklounge-2015.json`, 13KB)
이고 **원본 pcap 은 커밋하지 않는다** — 우리 저작물이 아니고 25~200MB 다. Siemens
권고문과 같은 취급이고 `scripts/fetch_pcap.py` 로 다시 받는다.

### 이게 바꾸는 주장 — "토폴로지가 100% 합성" 이 더는 전부가 아니다

ADR-013 은 경로 탐지 정확도를 주장하지 않는 이유로 **"토폴로지가 100% 합성"** 을
들었다. 이제 엣지가 **관측**에서 나온 토폴로지가 하나 있다. 그래도 **결론은
그대로다** — 이유가 더 정확해질 뿐이다:

- 4SICS 는 **컨퍼런스 시연 랩이고 공장이 아니다.** 게스트 WiFi 가 섞여 있다.
- **정답이 없다.** "그때 실제로 어떤 경로가 존재했는가" 를 아는 사람이 없으므로
  재현율·정밀도를 계산할 대상이 없다.

그래서 새 문장은 이렇다: *경로 탐지 정확도를 주장하지 않는다 — 정답 집합이 없고,
실제 트래픽에서 나온 토폴로지는 공장이 아니라 시연 랩이다.* 전보다 짧아지지 않았고,
**덜 변명스러워졌다.**

### 합성 픽스처로는 절대 안 보이던 false safe

실제 캡처를 넣자마자 드러났다. 이 7시간 창에서 **ICS 랩 대역(`10.10.10/24`)과
게스트망(`192.168.88/24`)은 서로 통신한 적이 없다.** 교차 엣지가 0개다. 그래서:

```
경로 0개  →  evaluate_reachability  →  Tri.FALSE
            "토폴로지상 진입점에서 도달하는 경로가 없습니다"
```

**캡처는 시간 창이다.** ADR-039 가 정확히 이것을 막으려고 만든 규칙인데
(`capture.py` 는 `observed` 엣지만 만들고 없는 쌍을 지어내지 않는다), 도달성은 그
사실을 **모르고** 공장에 대해 '닿지 않는다' 고 단정했다. 하류에서 노출 버킷이
`P?`(판단 불가) 대신 `P3`(낮다고 판단)이 되고 H02 가 FALSE 가 된다 — ADR-045 에서
고친 두 건과 **같은 가족의 세 번째**다.

고친 방법: 토폴로지의 **출처가 판단을 바꾼다.** `provenance.source` 가 캡처류
(`pcap`·`zeek`·`flow`)면 엣지 부재를 근거로 쓰지 않고 UNKNOWN 을 준다.

```
이 토폴로지는 캡처에서 나왔고 캡처는 **시간 창**입니다 — 그 창에서 닿는 길을
보지 못했을 뿐이고, 경로가 없다는 뜻이 아닙니다.
```

**반대 방향도 지켰다.** 사람이 손으로 선언한 토폴로지는 "여기 없는 연결은 없다" 를
사람이 책임지고 말한 것이므로 여전히 FALSE 를 낸다. 전부 UNKNOWN 으로 뭉개면
판정이 사라진다.

그리고 **구역을 선언해도 창은 창이다** — `zonemap` 을 덧입혀 레벨이 다 채워져도
엣지는 여전히 캡처에서 온 것이므로 UNKNOWN 이다. 전용 테스트가 그것을 고정한다.

### 교훈 — 입력의 *모양*이 아니라 *출처*가 판단을 바꾼다

ADR-045 는 "골드셋 하나로 다 지나간다고 믿지 말 것" 이었고 거기서는 **입력의 모양**
(진입점 유무, 레벨 None)이 문제였다. 이번 것은 한 걸음 더 간다: 모양이 같아도
**어디서 왔는지**가 다르면 같은 사실을 다르게 읽어야 한다. 엣지 0개는 손으로 쓴
그래프에서는 사실이고 캡처에서는 미상이다.

`provenance` 를 장식으로 두지 말 것 — 판정이 그것을 읽는다.

### 검토했고 쓰지 않은 것

| 데이터 | 왜 안 썼나 |
|---|---|
| **HAI** (국가보안기술연구소/ETRI 부설, 한국) | **CC BY-SA 4.0** 이다. 복제허락(ShareAlike)이라 MIT 저장소에 담으면 파생물 라이선스가 충돌한다. 그리고 **pcap 이 없다** — 공정 시계열 CSV 뿐이라 네트워크 토폴로지가 나오지 않는다. 테스트베드 구성(Emerson Ovation · GE Mark VIe · Siemens S7-300/S7-1500 · dSPACE HIL)은 논문에 공개돼 있으니 **참고**는 하되 데이터는 담지 않는다 |
| **SWaT · WADI** (iTrust/SUTD) | 신청서를 내고 받는 데이터이고 재배포 조건이 자유롭지 않다 |

처음 검색 요약은 HAI 를 `CC BY 4.0` 이라고 했는데 **저장소 원문을 확인하니
`CC BY-SA 4.0`** 이었다. 라이선스는 요약을 믿지 말고 원문을 볼 것.

## ADR-047 · 구역을 선언한다 — 캡처가 모르는 것을 사람이 적는다

`capture.py` 는 `purdue_level=None` · `zone=None` 을 만든다. 패킷에 그 정보가 없으니
옳다 (ADR-039). 그런데 **채울 방법이 없었다.**

레벨이 미상이면 도달성이 확정되지 않고(ADR-045) H01~H03 이 막혀 **첫 화면이 전부
`P?` 로 찬다.** 엔진은 정확히 옳게 동작하는데 현업자는 "이 도구는 아무것도 못
말하네" 로 읽는다. 현업자 시선 감사가 이것을 1순위 채택 저지 요인으로 꼽았다.

### 현업자가 아는 모양 그대로 받는다

```json
{"cidr": "10.10.10.0/24",  "zone": "제어망",   "purdue_level": 1, "is_critical": true}
{"cidr": "0.0.0.0/0",      "zone": "외부",     "purdue_level": 5, "is_entry_point": true}
```

**먼저 쓴 규칙이 이긴다.** 접두 길이로 자동 정렬하지 않는다 — 사람이 적은 순서가
사람의 의도이고, 자동으로 바꾸면 `0.0.0.0/0` 을 맨 위에 둔 사람의 "전부 외부로 보되
아래에서 예외" 라는 의도가 조용히 뒤집힌다.

`--zones-template` 이 보이는 대역을 /24 로 묶어 **빈 서식**을 만든다. 레벨을
추측해서 채워 주지 않는다 — 추측이 사실로 굳는다.

### 선언은 관측이 아니다

채운 값마다 노드 증거에 남긴다:

```json
"evidence": {"source": "pcap", "packets": 84605,
             "declared_by": "zonemap", "declared_fields": ["zone", "purdue_level"],
             "zonemap_sha256": "…"}
```

관측 증거를 **지우지 않고** 그 옆에 선언을 적는다. 섞으면 "이 레벨을 누가 정했나" 에
답할 수 없다 (불변 규칙 5: 계보 100%). 그리고 **이미 아는 값은 덮지 않는다**
(불변 규칙 3: Assertion 은 추가만).

### 규칙에 안 걸린 노드는 비워 둔다

기본값을 주지 않는다. `purdue_level=0` 으로 채우면 모르는 장비가 전부 물리 제어
계층이 되고 `critical_nodes()` 가 그것을 안전 핵심 표적으로 센다 — ADR-039 가 막은
것이다. 안 걸린 노드는 수를 세어 보고한다.

### 남은 것

- **자산대장의 `구역` 열에서 골격 토폴로지를 만드는 길은 아직 없다.** 지금은 캡처가
  있어야 노드가 생긴다. xlsx 로 들어온 800대가 그래프 안에 존재하게 만드는 것이
  다음 일이다 (`GAP_ANALYSIS.md`).
- 구역 **사이**의 연결은 선언할 수 없다. 노드 속성만 채운다 — 엣지를 손으로
  선언하는 길은 아직 토폴로지 JSON 을 직접 쓰는 것뿐이다.

## ADR-046 · 현장 자산대장이 실제로 들어가게 한다

현업자 시선으로 "다음 달부터 쓸 수 있나" 를 감사했다. 엔진에 쓸 공수는 0이었고
막는 것은 전부 **반입·저작·내보내기·일정** 이라는 껍데기였다. 그 첫 칸이다.

### CP949 를 거절하고 있었다 — 첫 시도가 100% 실패했다

한국 Excel 의 「CSV(쉼표로 분리)」 **기본 저장이 CP949** 다. `safeio` 는
`utf-8-sig` 하나만 받으면서 이렇게 안내했다:

> UTF-8 로 읽을 수 없습니다 — 엑셀에서 'CSV UTF-8' 로 다시 저장해 주세요

문장은 친절하지만 **설비 800대를 공장별 시트마다 다시 저장하라는 뜻**이고, 그걸
매달 반복하라는 뜻이다. 도입 결정이 거기서 끝난다.

`TABLE_ENCODINGS = ("utf-8-sig", "cp949")` 로 **순서 있게 시도**한다. 추측이
아니라 '읽히는 것' 으로 정한다. 둘 다 아니면 그때 사람에게 묻는다.

그리고 **무엇으로 읽었는지 보고서에 싣는다.** 글자가 깨진 채 조용히 들어가면
`제조사` 가 깨져 식별이 통째로 실패하는데 화면에는 그냥 '일치 항목 없음' 으로
뜬다 — 불변 규칙 1 의 입구다.

### 엑셀을 읽는다. 머리글 행은 짐작하지 않는다

현장 대장의 실제 모양: 1행 병합 제목("○○정밀 설비 자산대장"), 2행 작성자, 3행 빈
줄, **4행 머리글**. 그리고 공장별 시트마다 다르다 — 2공장 시트는 1행이 머리글이다.

짐작하면 제목 행을 머리글로 삼은 채 800대가 들어온다. 그래서 `xlsxread.scan()` 은
**후보를 점수(★)와 함께 제시**하고 고르는 것은 사람이다:

```
  [1공장]  4행  ★★★  걸린 열 7개: 설비번호, 설비명, 제조사, 모델명, 펌웨어, 구역, 담당자
  [2공장]  1행  ★★★  걸린 열 7개: …
이대로 읽으려면:  --sheet 1공장:4 --sheet 2공장:1
```

**xlsx 는 zip + xml 이다.** `openpyxl` 이 그 xml 을 파싱하므로 압축폭탄과
DTD(내부 엔티티 폭탄)를 **우리가 먼저** 막는다 — `inspect_zip` + `reject_dtd`
(ADR-038 에서 347바이트가 100만 자가 됐던 그 방어다). `openpyxl` 은 순수
파이썬이라 폐쇄망 반입에 플랫폼 wheel 이 필요 없다 (불변 규칙 9). 선택 extra
`.[xlsx]` 로 둔다 — CSV 만 쓰면 없어도 된다.

### 자산에 사람이 읽을 이름이 없었다

실측: 실제 한국 대장 머리글 중 **설비명 · 위치 · 담당자가 버려졌다.** 동의어 표에
없었고, 담당자는 **모델에 필드 자체가 없었다**. 결과적으로 목록에 `PLC-001` 만
뜨고 "프레스 3호기" 는 사라져 **현장 사람이 자기 설비를 못 찾는다.**

| 추가 | 왜 |
|---|---|
| `Asset.label` | 사람이 읽는 설비명. **식별에 쓰지 않는다** — 현장이 붙인 이름이고 제조사의 제품명이 아니다. 화면에서 자기 설비를 찾는 데만 쓴다 |
| `Asset.ownership` | 담당자·부서. 조치를 사람에게 붙이는 **유일한 고리**다. CISA 자산 인벤토리 지침의 Department/Owner 항목이고 `GAP_ANALYSIS.md` 가 ❌ 로 자인하고 있었다 |

둘 다 기본값이 있어 기존 픽스처와 DB 행이 그대로 읽힌다.

### 매핑을 매달 다시 하지 않는다

`ImportProfile` 에 사람이 고른 **매핑과 시트:머리글행**을 남긴다. `--save-profile`
로 남기고 `--profile` 로 다시 쓴다. 추론은 여전히 후보를 제시할 뿐이고 프로파일이
이긴다 — 그 규칙은 원래부터 `build_report(mapping_override=...)` 가 쥐고 있었고,
여기는 그 값을 **담아 두는** 자리다.

회사 대장의 열 이름이 그대로 들어가므로 `data/import-profiles/` 는 커밋하지 않는다.

### 입구만 둘, 뒤 단계는 한 함수

`build_report_from_rows(headers, rows, …)` 를 CSV 와 엑셀이 공유한다 — 매핑 ·
수식 인젝션 무해화 · 미상 보존 · 중복 검사 전부. 복사하면 한쪽을 고칠 때 다른 쪽이
조용히 달라진다. **이 저장소가 반복해서 겪은 실수다** (`_cmd_controls` 의 `kev`
누락, `evidence_for` 의 코드별 분기).

### 커버리지 없는 제조사를 '안전' 으로 읽히게 두지 않는다

실측 — 권고문 1,306건에 한국 공장 흔한 제조사가 등장하는 횟수:

| | | | |
|---|---:|---|---:|
| Siemens | 361건 | Mitsubishi | 43건 |
| Rockwell/AB | 138건 | Delta | 35건 |
| Schneider | 95건 | **LS ELECTRIC** | **1건** |
| Hitachi | 57건 | **Omron · Keyence · Panasonic · Hyundai** | **0건** |

**LS산전 PLC 120대를 넣으면 CVE 축이 거의 전부 '알려진 일치 없음' 이다.** 도구
결함이 아니라 그 제조사가 기계 판독 가능한 권고문(CSAF)을 내지 않는다. 그런데
화면이 그 사실을 말하지 않으면 현업자는 "쓸모없네" 아니면 **더 나쁘게 "우리 공장
괜찮네"** 로 읽는다.

반입할 때 그 제조사를 세어 **이름을 부르고, 대신 무엇으로 보는지 말한다.** 실측으로
확인했다 — LS ELECTRIC XGK-CPUH 한 대를 **권고문 0건**으로 돌리면:

```
노출·구성 위험 2건   평문 제어 통신 · 원격접속 MFA 없음
KISA 점검 항목       근거 있음 6건
NIST OT Overlay      근거 있음 5건
```

노출·경로·점검 항목 축은 **권고문 없이도 돈다** (ADR-035 가 CVE 와 노출을 분리해
둔 덕이다). 그래서 저 안내는 측정된 주장이다.

### 남은 것

- **담당자에게 일을 배정하고 완료를 추적하는 길은 없다.** 필드는 생겼지만 발견에
  `open/done` 상태가 없다. 감사는 그걸 만들지 말고 **CSV 로 빼서 Jira·Redmine 에
  넘기라**고 권했고, 그게 맞다 — 그 내보내기가 다음 일이다.
- 웹 화면은 아직 `mapping` 을 보내지 않는다. CLI 는 되고 API 는 받을 준비가 돼
  있는데 화면에 입구가 없다 — 지금은 CSV 붙여넣기만 가능하다.
- `.xlsx` 쓰기는 안 한다 (읽기만). 보고서 내보내기에서 다시 볼 일이다.

## ADR-045 · 공개 후 감사 — 골드셋이 닿지 않는 입력 모양

ADR-041 이 공개 **전** 점검이었다. 이것은 공개 **후** 감사다. 찾은 것 중 셋은
불변 규칙 1(false safe 0건)을 **실제로 어기고 있었다.**

### 왜 테스트가 전부 녹색이었나 — 입력 모양이 하나였다

셋 다 도달성 판정에 있었고, 셋 다 `fixtures/topology/purdue-62443-reference.json`
으로는 밟히지 않는다. 그 픽스처는 **진입점이 선언돼 있고 Purdue 레벨이 전부
채워져 있다.** 그런데 `capture.py` 가 만드는 토폴로지는 반대다:

| | 골드셋 픽스처 | 캡처에서 만든 것 |
|---|---|---|
| `is_entry_point` | `internet` · `vendor-remote` | **없다** (패킷에 그런 개념이 없다) |
| `purdue_level` | 전부 채워짐 | **전부 `None`** (`capture.py` 가 그렇게 쓴다) |
| `Edge.grants` | 선언됨 | 선택 필드 — 비어 있을 수 있다 |

ADR-039 는 이 빈칸을 "사람이 채워야 합니다" 로 문서화했다. **그 중간 상태가
정상 경로다.** 그런데 그 상태를 지나는 테스트가 없었다.

### 1. 진입점을 모르는 것이 '닿지 않는다' 가 됐다

`evaluate_reachability` 는 `topo is None` 과 `node is None` 만 막았다. 토폴로지에
**진입점이 0개**인 경우는 `find_paths` 가 빈 결과를 주고, 그대로 마지막 줄
`Tri.FALSE`("진입점에서 도달하는 경로가 없습니다")로 떨어졌다.

하류가 조용히 틀어진다:

| | `Tri.FALSE` (전) | `Tri.UNKNOWN` (후) |
|---|---|---|
| 노출 버킷 | **`P3`** — 도달성이 낮다고 *판단한* 것 | **`P?`** — 판단 자체가 불가능한 것 |
| H02 | FALSE → `P?` 큐에도 안 들어온다 | UNKNOWN → `floor_if_confirmed` 와 함께 보류 |

`P?` 를 만든 이유(ADR-007)가 정확히 이 구분인데, 그 구분이 입구에서 무너져 있었다.

### 2. 능력 근거가 없는 것이 '경로가 없다' 가 됐다

`require_capability` 필터가 **비어 있지 않던** 목록을 비우면 같은 마지막 줄로
떨어져 *"진입점에서 도달하는 경로가 없습니다"* 라고 말했다. **경로는 있다.**
없는 것은 그 경로가 요구 능력을 준다는 근거다. `Edge.grants` 가 선택 필드이므로
손으로 만든 토폴로지도 캡처에서 나온 토폴로지도 다 걸린다.

이건 false safe 이면서 동시에 **사실이 아닌 문장**이었다. 화면에 "경로 없음" 이
떠 있는데 경로가 있다.

### 3. `purdue_level` 이 `None` 이면 H03 이 터졌다

`priority.py` 의 `topo.nodes[p.entry].purdue_level >= 4.0` 가
`TypeError: '>=' not supported between 'NoneType' and 'float'` 로 죽는다.
H03 평가가 죽으면 `otai queue` 와 `/api/actions` 가 같이 죽는다.

`topology.py` 는 **같은 비교를 이미 막고 있었다**(`if lvl is not None and lvl <= 0.0`,
주석까지 달려 있다). 규율이 한 모듈에서 다음 모듈로 넘어가지 않았다.

그리고 레벨을 모르는 진입점은 외부도 내부도 아니다 — 고친 뒤에도 '모두 내부'
(`Tri.FALSE`)라고 하면 **모르는 것을 근거로 H03 을 끄는 것**이다. `UNKNOWN` 이다.

### 막는 방법 — 입력 모양을 테스트가 들고 있게

`tests/test_false_safe_guards.py` 에 다섯 개를 더했다. 마지막 하나가 중요하다:

```python
def test_capture_topology_shape_is_the_one_that_trips_these():
    assert gold.entry_points, "골드셋은 진입점이 있다 — 그래서 #1 을 안 밟았다"
    assert all(n.purdue_level is not None for n in gold.nodes.values())
```

**왜 안 걸렸는지를 테스트가 말한다.** 골드셋의 모양이 바뀌면 이 테스트가 먼저
깨지고, 그때 나머지 넷이 무엇을 지키고 있었는지 다시 읽게 된다.

반대 방향도 고정했다 — 엣지가 진짜 없으면 여전히 `Tri.FALSE` 다. 전부 UNKNOWN 으로
뭉개면 판정이 사라진다.

### HTTP 본문은 우리가 보기 전에 파싱된다

`body: dict = Body(...)` 는 Starlette 가 파싱한 뒤 핸들러에 들어온다. 우리 코드가
돌기 전이라 `MAX_JSON_BYTES` · `MAX_JSON_DEPTH` 가 **전부 건너뛰어졌다.** POST
라우트 5개가 그랬고 그중 `/api/assets` 는 append-only 저장소에 바로 쓴다 —
인증도 CSRF 토큰도 없다. `otai/server.py` 의 단순한 입력 서버는 이미 본문을 묶고
있었는데(`if n > 1 << 20`) FastAPI 계층만 물려받지 못했다.

**핸들러를 `async` 로 바꾸지 않았다.** 바꾸면 동기 DB 쓰기가 스레드풀이 아니라
이벤트 루프에서 돌아 스윕 스레드와 함께 서버를 멈춘다. 대신 ASGI 미들웨어
(`BoundedBody`)가 본문을 모아 검사하고 **그대로 다시 흘려보낸다** — 지금 라우트와
앞으로 추가될 라우트가 모두 덮이고 핸들러는 동기로 남는다.

`safeio.check_json_bounds` 를 더했다 — 크기·깊이만 보고 **파싱하지 않는다.**
`bounded_json_loads` 를 쓰면 FastAPI 가 파싱할 본문을 두 번 파싱한다.

**그리고 이 미들웨어가 회귀를 하나 만들었다 — 고쳤다.** 첫 판은 모든 POST 에
`MAX_JSON_BYTES`(64MB) 하나를 걸었다. 그런데 캡처와 프로젝트 파일은 프런트엔드가
`FileReader.readAsDataURL` 로 **base64 로 실어 보낸다**(`content_base64`). 본문이
원본의 약 4/3 배가 되므로, 캡처 엔진이 `MAX_CAPTURE_BYTES`(512MB)까지 받는데
**웹에서는 48MB 쯤에서 413 이 나고 CLI 와 웹이 갈렸다.** 실측: 70MB pcap →
base64 93MB → `413 본문 크기 초과`.

경로별 상한을 각 `safeio` 상한에서 역산한다(`BoundedBody.LIMITS`): 캡처 683MB ·
프로젝트 파일 85MB · CSV 43MB · 그 외 64MB. 한 수를 전부에 걸면 파일 라우트가
막히고, 가장 큰 수를 전부에 걸면 평범한 JSON 라우트가 512MB 를 받는다.

텍스트 검사(깊이·UTF-8)는 **스스로 폼·바이너리라고 밝힌 content-type 만** 건너뛴다.
`multipart/` · `octet-stream` · `x-www-form-urlencoded`. content-type 이 없거나
모르는 값이면 검사한다 — 우리 라우트는 전부 JSON 이므로 그쪽이 안전한 기본값이다.
앞으로 업로드 라우트가 생겼을 때 바이너리 본문을 **없는 문제로 거절**하지 않기
위한 것이다.

### 감사의 권고를 하나 따르지 않았다

`Tri.and_()` 가 인자 0개에서 `TRUE` 인 것을 `UNKNOWN` 으로 바꾸라는 권고가 있었다.
**따르지 않았다.** `tests/test_versions.py` 가 항등원을 명시적으로 고정하고 있고
(`assert Tri.and_() is Tri.TRUE`), 그게 올바른 Kleene 대수다. 논리 기본형을
비틀면 다른 곳에서 설명할 수 없는 동작이 생긴다.

위험은 기본형이 아니라 **호출처**였다 — 전제조건이 빈 `HardRule` 이 무조건
발화하는 것. `HardRule.__post_init__` 이 선언 시점에 막는다. 규칙 5개는 전부
전제조건을 갖고 있어 지금은 도달하지 않지만, 새 규칙을 쓸 때 터진다.

### 그 밖에

| 찾은 것 | 왜 문제인가 |
|---|---|
| `docs/VERIFICATION.md` 가 326건 (실제 521) | `verify_matrix.py` 의 파일 목록이 **하드코딩**이라 ADR-037 이후 6개 파일 190건이 빠졌다. README 가 세 번 '검증의 근거' 로 가리키는 문서가 자기 범위를 36% 적게 말했다 |
| `demo.py` 가 `ssa-452276.json` 을 찾는다 | `fetch_advisories.py` 는 `ssa-019113.json` 을 받는다 → 6단계가 **영구히 건너뛰어졌다.** 고치자마자 ADR-031 위반이 드러났다(CVE 431건을 한 줄에 쏟았다) |
| `pyproject` 의 `testpaths = ["tests"]` | `tests/` 를 배포하지 않으므로 내려받은 사람의 첫 `pytest` 가 죽는다 — 없는 것을 고장으로 보이게 만들었다 |
| `cli.py --mapping` · `csvimport` · `bundle` 매니페스트 · `fetch_advisories` KEV · `inventory` | safeio 우회 5곳. `safeio` 머리의 "`csv.reader` 를 직접 부르지 말 것" 은 **읽기가 없어서 지킬 수 없는 말**이었다 → `bounded_csv_rows` 를 만들고 상한을 한 곳으로 모았다 |
| `capability.describe(frozenset())` → `"없음"` | 빈 집합이 나오는 길은 'CVSS 벡터 없음'·'`grants` 미선언' 둘뿐이고 **정말 능력이 없음을 확인한 경우는 없다.** 경로 화면에서 '이 홉은 안전' 으로 읽힌다 → `"미상"` (ADR-031) |
| `api.py` 의 `verdict.value == "true"` | `Tri.__bool__` 가드를 지나쳐 문자열을 본다. 타입이 바뀌면 조용히 거짓이 되고, 여기서 거짓은 안전하지 않은 방향이다 |
| 같은 수를 두 곳에서 다르게 (제품명 4,595/4,581 · 성능 0.62/0.63 · 테스트 34/45) | 세어서 맞췄다. 제품명은 실측 **4,581**. 성능은 README 가 수를 다시 적지 않고 측정표를 가리키게 했다 — 한 수에 출처 하나 |

`otai/repo.py` 의 `json.loads` **셋은 그대로 둔다.** 우리 DB 안의 값이고 들어올
때 이미 한계를 거쳤으며, 목록 화면이 모든 행을 파싱하는 핫 경로다. 이유를
주석으로 적었다 — 외부 바이트가 그 경로로 들어오게 만들지 말아야 한다.

### 남은 것

- **웹 화면에서 점검 항목 근거를 볼 수 없다** (`GAP_ANALYSIS.md` (h)). CLI 는 붙었다.
- `otai ask` 서버와 FastAPI 가 본문 한계를 **각자** 들고 있다. 합칠 수 있다.
- `_cmd_controls` 가 `queue` 와 같은 파이프라인이라고 적으면서 `kev` 를 빼먹고
  있었다 — H01·H03 이 CLI 에서 절대 발화하지 않았다. 지금은 `hard_rule_H01` 을
  가리키는 항목이 없어서 안 보이지만, 더하는 순간 조용히 침묵한다. `--kev` 를
  더하고 `find_snapshot()` 으로 기본값을 잡는다. **'같은 파이프라인' 이라고 쓸
  때는 인자까지 같은지 보라.**
- ~~`cli.py` 와 `api.py` 가 `verdict.value` 를 표시한다~~ → **고쳤다.** `Tri.ko`
  (예 / 아니오 / **미상**)를 `logic.py` 에 두고 두 곳이 그걸 쓴다. 매핑을 클래스
  본문 안에 두면 **enum 멤버로 잡히므로**(실제로 그랬다) 클래스 밖에 둔다.

## ADR-044 · 표준을 둘 싣는다 — 근거는 하나로 모은다

ADR-043 에서 NIST 쪽은 **Rev.3 영문 원문이 필요하다**고 적고 미뤘다. 받아서 했다.

### 받은 것

`NIST SP 800-82 Rev. 3 — Guide to Operational Technology (OT) Security`
(2023-09, 316쪽, https://doi.org/10.6028/NIST.SP.800-82r3). Rev.2 는 2023-09-28 에
withdraw 됐고 이것이 대체판이다. 표지에 **"not subject to copyright in the United
States. Attribution would, however, be appreciated by NIST"** — 미국 정부 저작물이라
KISA 번역본과 달리 **인용할 수 있다.**

우리가 읽은 곳은 **부록 F — OT Overlay**(230~315쪽)다. SP 800-53 Rev.5 통제를 OT 에
맞춰 재단한 것으로, 다루는 통제가 **229개 · 19개 통제군**이다.

**인용할 수 있어도 본문을 옮기지는 않는다.** 통제 ID·이름·통제군과, 매핑한 11개
항목에 한해 근거가 된 **OT Discussion 의 짧은 인용**만 싣는다(최대 229자, 합계
1,249자). 통제 본문은 800-53 Rev.5 에 있고 오버레이 자신도 그것을 복제하지 않는다.
원문 PDF 는 `.gitignore` 로 막았다 — 받는 곳이 공개 URL 이라 다시 받으면 된다.

### 229개 중 11개

| 범위 | 수 | 통제 |
|---|:--:|---|
| **직접 근거** | 2 | `CM-8` System Component Inventory · `SA-22` Unsupported System Components |
| **일부만** | 9 | `AC-4` · `CM-7` · `IA-3` · `RA-3` · `RA-5` · `SC-7` · `SC-8` · `SI-2` · `SI-4` |
| **도구 범위 밖** | 218 | 정책·절차·물리·인적·비상계획·공급망 등 |

매핑은 **OT Discussion 원문을 읽고** 정했다 — 통제 이름만 보고 짐작하지 않았다.
오버레이가 OT 맥락을 덧붙이지 않은 통제(`CM-8` 이 그렇다)는 800-53 원문이 그대로
적용된다는 사실까지 적었다.

읽은 내용이 우리 설계와 같은 말을 하는 곳이 많았다. `SI-2`(Flaw Remediation)는
*"the organization has no choice but to accept additional risk if no vendor patch is
available"* 라고 적는다 — H04 의 '무조건 패치 표현 금지'(표 23)와 같다. `SA-22` 의
*"identify alternative methods … and consider additional compensating controls"* 는
우리 차단 후보와 같은 자리다. `SC-7` 은 *"selects an appropriate failure mode"* 를
요구하고, `SI-4` 는 *"monitoring … does not adversely impact the operational
performance of the OT"* 를 요구한다.

### 답하지 않는 것을 통제 단위로 적었다

- **`RA-5`(Vulnerability Monitoring and Scanning)는 절반만이다.** 모니터링 쪽은 답한다.
  **스캐닝은 하지 않는다** — 능동 질의 금지는 불변 규칙 6 이고, 통제가 요구해도
  바꾸지 않는다. 그 사실을 근거 문장에 싣는다.
- **`SI-4`(System Monitoring) — 우리는 모니터링 시스템이 아니다.** 사용자가 준 캡처의
  시간 창만 읽고 망에 아무것도 보내지 않는다. 오버레이가 요구하는 '운영 성능에 영향
  없음' 은 그래서 자동으로 성립하지만, **지속 탐지는 별도 시스템이 필요하다.**
- **`CM-7`(Least Functionality) — '운영에 필요한 통신인가' 를 우리가 정하지 않는다.**
  열린 제어 프로토콜은 센다. 하지만 공정 요구를 모르는 채 불필요로 단정하면 가동을
  멈추는 조치를 권하게 된다.
- **`CM-8` 은 직접 근거인데 설치 소프트웨어 목록이 빈다.** SBOM 입력이 필요하다
  (`GAP_ANALYSIS.md` 항목 b). 직접 근거라고 적고 빈 칸을 숨기지 않는다.
- **`RA-3`(Risk Assessment)은 위험평가의 입력이지 위험평가가 아니다.** P0~P4 정확도를
  주장하지 않는다는 ADR-008 이 여기서도 그대로다.

### 항목 코드로 분기하지 않는다 — 근거 종류로 모은다

ADR-043 의 `evidence_for` 는 `if code == "C-18"` 로 분기했다. 항목 9개일 때는 읽혔다.
**표준이 둘이 되면 깨진다**: `C-18`(알려진 취약점 대응)과 `SI-2`(Flaw Remediation)는
다른 어휘로 같은 것을 묻고 같은 근거를 쓴다. 코드마다 로직을 따로 쓰면 한쪽을 고칠 때
다른 쪽이 조용히 멈춘다.

그래서 근거를 **`evidence_kind` 종류별로 한 번** 만들고(`_gather`), 항목은 자기가
쓰는 종류를 가리킨다. 실측: 생산자 **16종**, KISA 가 9개 항목에서 **15종**을, NIST 가
11개 항목에서 **14종**을 가리킨다(겹치는 것 13종). 덕분에 `no_known_match` 를 근거로
세지 않는 보호(불변 규칙 1)가 NIST 쪽에 **따로 쓰지 않아도** 걸린다 — 전용 테스트가
그것을 확인한다.

표준마다 다른 것은 **무엇에 대한 근거로 말하는가**다. 같은 도달성 판정을 KISA `C-21`
은 '망 분리', NIST `SC-7` 은 '경계 보호' 로 받는다. 그 어휘만 `_SEPARATION` 에 두고,
사실은 한 곳에서 만든다.

### 가리키는 이름에 생산자가 없으면 조용히 사라진다

첫 생성본은 `kev` · `prefilter_sweep` · `attack_techniques` · `priority_buckets` 를
가리켰다. **`evidence_for` 에 그런 입력이 없다.** 그대로 두면 `RA-5` 와 `RA-3` 은
입력이 다 있어도 '근거 없음' 이 되고, 화면에는 아무 문제도 안 보인다 —
`exposure.CONTROL_PROTOCOLS` 에서 `opcua` 가 빠졌던 것과 같은 함정이다 (ADR-040).

막는 것 둘:

| 테스트 | 막는 것 |
|---|---|
| `test_every_referenced_kind_has_a_producer` | 표준이 **없는 이름**을 가리키는 것. 실린 표준 전부를 훑는다 |
| `test_every_assessable_control_can_reach_present` | 근거가 다 있는 자산에서 답할 수 있다고 적은 항목이 **하나라도** 침묵하는 것 |

**두 테스트가 잡은 것과 잡지 않은 것을 구분해 적는다.** 네 이름이 가짜인 것은
테스트가 아니라 종류 목록을 찍어 보고 알았다 — 테스트는 그것이 **다시 생기는 것**을
막는다. 그리고 `C-08`·`C-12` 의 이름(`exposure_finding`)이 묻는 것(`plaintext_control`,
암호 없는 제어 통신)과 달랐던 것은 **옛 코드를 읽고** 고쳤다. 옛 코드는 이 둘에
C-18 과 다른 문장(평문 제어 통신 전용)을 내고 있었는데 종류 이름이 그걸 담지 못했다.
테스트가 이걸 잡지는 **못했다** — `exposure_finding` 도 같은 `exposures` 입력에서
발화하므로, 틀린 문장을 내면서 '근거 있음' 이 됐을 것이다.

두 테스트가 실제로 막는 것은 **앞으로의 배선 실수**다. `C-08`·`C-12`·`C-24`·`C-26` 과
NIST 11개는 대부분 항목별 테스트가 없어서, 종류 이름이 하나 틀어지면 조용히 멈춘다.

반대 방향도 본다 — 아무 표준도 쓰지 않는 생산자가 남아 있으면 죽은 코드다.

### `find_set` 하나만 고르던 것

`find_set()` 은 `data/controls/*.json` 중 **첫 파일**을 돌려줬다. 파일이 하나일 때는
맞았다. 두 번째가 들어오면 알파벳 순으로 KISA 가 먼저이므로 **NIST 표가 통째로
보이지 않는다.** `find_sets()` · `load_all()` 로 바꾸고, 예전 이름은 호출자를 위해
남겨 둔다. 테스트는 전부 `find_sets()` 를 돌며 표준마다 한 번씩 실행된다 —
세 번째 표준(62443)이 들어오면 검사도 자동으로 따라간다.

### 남은 한계

- **CLI 는 붙었고 웹 화면은 없다.** `otai controls` 가 `queue` 와 **같은 파이프라인**
  으로 판정·노출·도달성을 만들어 근거로 넘긴다 — 여기서 따로 계산하면 두 화면이
  다른 수를 말한다. 웹 화면(표 25)과 보고서 내보내기는 남았다 (`GAP_ANALYSIS.md` (h)).
  감사 행위 `controls_evidence_listed` 를 등록했다 — 읽기만 하지만 누가 어느 시점의
  근거를 들고 나갔는지가 평가 자료의 출처가 된다.
- **기준선(LOW/MOD/HIGH) 선정과 재단은 조직이 한다.** 오버레이는 통제마다 기준선과
  OT 전용 보강을 말하는데, 우리는 그 선정에 관여하지 않는다. `severity` 가 KISA 는
  상/중/하이고 NIST 는 비어 있는 이유다 — 없는 값을 지어내지 않는다.
- **이 매핑도 한 사람이 읽고 만든 것**이다. 통제별 `note` 에 무엇을 근거로 봤는지
  적어 두었으니 이견이 있으면 그 줄을 고친다.
- **통제 보강(enhancement, 예: `AC-4(21)`)은 매핑하지 않았다.** 오버레이가 기준선에
  올린 보강이 있지만 상위 통제 단위로만 답한다.
- **IEC 62443-3-3 은 아직 없다.** 표준 셋이 되면 `SR 1.1` 같은 요구사항 코드가
  더해지는데, 근거는 이미 종류별로 모여 있으므로 표 하나를 더하는 일이다.

## ADR-043 · 점검 항목에 근거를 댄다 — 준수를 판정하지 않는다

**받은 것**: KISA 「주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드」
**2026년판**(873쪽)과 NIST SP 800-82 Rev.2 한글 번역본(353쪽).

### 둘 중 하나만 쓴다

**KISA 가이드의 `06. 제어시스템` 장(469~552쪽)이 정확히 우리 영역이다.** 점검항목
**C-01 ~ C-51**, 9개 분류(계정·서비스·패치·네트워크 접근통제·물리적 접근통제·
보안위협 탐지·복구 대응·보안 관리·교육 훈련), 항목마다 중요도(상/중/하)가 붙어 있다.

**NIST 800-82 Rev.2 는 매핑 근거로 쓰지 않는다.** 두 가지 이유:

1. **폐기된 판이다.** NIST 가 2023-09-28 에 withdraw 하고 Rev.3 으로 대체했다
   (csrc.nist.gov 에서 확인). Rev.2 의 부록 G(ICS 오버레이)는 800-53 Rev.4 기준이고
   Rev.3 은 Rev.5 로 다시 깔았다 — 통제 ID 가 달라졌다. 폐기된 ID 로 매핑을 만들면
   감사에서 자산이 아니라 부채가 된다.
2. **번역본 저작권이 KISA 에 있다.** 표지에 "무단 복제, 무단 배포 등을 금합니다" 가
   있다. 용어 참고로는 쓰되 인용하지 않는다.

NIST 쪽을 하려면 **Rev.3 영문 원문**(미국 정부 저작물, 공공 도메인)을 받아야 한다.
→ **받아서 했다 (ADR-044).** 부록 F 의 OT Overlay 통제 229개 중 11개에 근거를 댄다.

### 무엇을 싣고 무엇을 싣지 않는가

| | |
|---|---|
| **싣는다** | 항목 코드 · 중요도 · 분류명 — 표준에 대한 **사실**이다 |
| **싣지 않는다** | 점검 내용 · 판단 기준 · 조치 방법 본문 — KISA 의 **저작물**이다 |
| 대신 | 우리가 쓴 60자 이내 한 줄 요약(`gist`) |

원문 PDF 두 개는 `.gitignore` 로 막았다 (Siemens 권고문과 같은 취급). 전용 테스트가
항목 행에 표준 본문 표지("판단 기준"·"양호 :"·"※" 등)가 섞이지 않았는지 검사한다.

### '준수' 라고 말하지 않는다

취약점 분석·평가는 **정보통신기반 보호법에 따라 자격을 갖춘 평가기관**이 수행한다.
「양호」·「취약」은 그쪽의 판정 어휘다. 우리가 쓰면 **할 수 없는 법적 주장**을 하는
것이다. 우리 어휘는 셋이다:

| 상태 | 뜻 |
|---|---|
| `evidence_present` **근거 있음** | 이 항목에 댈 기계 판독 가능한 근거를 냈다 |
| `evidence_absent` **근거 없음** | 낼 수 있는 항목인데 아직 근거가 없다. **미달이 아니다** |
| `not_assessable` **도구가 답할 수 없음** | 정책·절차·물리·교육 항목이다. **통과도 미달도 아니다** |

셋인 이유는 이 제품의 다른 모든 곳과 같다 — 답하지 못한 것을 '문제 없음' 으로
접지 않는다. 전용 테스트가 **출력 문장 전체**를 훑어 「양호」·「준수」·「적합」·
「미흡」이 섞이지 않았는지 본다.

### 51개 중 9개 — 그리고 42개를 그대로 싣는다

| 범위 | 수 | 항목 |
|---|:--:|---|
| **직접 근거** | 2 | C-18(알려진 취약점 대응) · C-50(허가에 의한 로직 변경) |
| **일부만** | 7 | C-08 · C-12 · C-19 · C-21 · C-24 · C-26 · C-43 |
| **도구 범위 밖** | 42 | 정책 수립·훈련·물리 보호·백업·교육 등 |

**우리가 답하는 9개만 싣고 42개를 빼면 안내서가 아니라 홍보물이 된다.** 51개를 전부
싣고 `our_scope: none` 을 그대로 보여준다.

### 일부만 답하는 것들의 정확한 경계

- **C-19 는 두 가지가 한 코드에 묶여 있다.** '기술지원 종료 제품 미사용' 은 제조사
  선언까지 확인해 답한다(`lifecycle.vendor_confirmed`, H04). **'최신 버전 사용' 은
  답하지 않는다** — '최신이 무엇인가' 를 아는 출처가 없고, 추정하면 ADR-038 의
  설정값 함정과 같은 오류가 된다.
- **C-21(망 분리)은 반증 쪽으로만 답한다.** 외부에서 이 장비까지 **모든 구간이 확인된**
  경로가 있으면 분리되지 않았다는 근거다. 경로를 못 찾은 것은 **'분리됐다' 가 아니다**
  — 캡처는 시간 창이고 토폴로지는 미완일 수 있다 (ADR-014/039).
- **C-43 은 우리 필드를 그대로 호명한다** — 담당자·제조사·모델명·펌웨어 버전·설치 SW.
  제조사·모델명·펌웨어는 식별 사다리와 L0~L5 로, 주소는 ADR-042 로 답한다.
  **담당자와 설치 SW 는 못 답한다** — 설치 SW 는 SBOM 입력이 필요하다
  (`GAP_ANALYSIS.md` 항목 b).
- **`no_known_match` 는 근거가 아니다.** '대상이 아니다' 를 C-18 의 근거로 세면
  불변 규칙 1 을 우회하는 것이다. 전용 테스트가 막는다.

  항목별 `note` 에 무엇을 근거로 봤는지 적어 두었으니 이견이 있으면 그 줄을 고친다.
- KISA 가이드의 나머지 11개 장(Unix·Windows·DBMS·네트워크 장비 등)은 매핑하지

## ADR-042 · 자산에 주소를 담는다 — 뽑아 놓고 버리던 값

**발견**: CISA 의 *Foundations for OT Cybersecurity: Asset Inventory Guidance* 는 OT 자산
인벤토리가 먼저 모아야 할 **고우선 속성 14개**를 지정한다. 우리 스키마를 실측하니 **9/14**.
못 담는 다섯 중 **IP·MAC**(그리고 중간 우선순위의 VLAN)은 `capture.py` 가 PCAP 에서
**이미 뽑아 놓고 버리던** 값이다 — 토폴로지 노드에만 싣고 자산에는 담을 자리가 없었다.

그래서 IP 로 만든 노드와 주문번호로 만든 자산이 **서로를 몰랐다.**

**결정**

1. **주소는 값이 아니라 관측이다.** `NetworkAddress(ip, mac, hostname, vlan, method,
   observed_at, evidence_id)`. 부품 버전과 같은 규율이다 (ADR-038) — 어디서 언제 알게
   됐는지가 함께 간다. `method` 는 `capture`(PCAP 관측) · `import`(사람이 CSV 로) ·
   `manual` · `project_file`.
2. **여럿일 수 있다.** 이중화 CPU·다중 NIC 는 예외가 아니라 기본이다. `Tuple` 로 담고
   접근자(`ips`·`macs`·`hostnames`·`vlans`)는 **순서를 지키며 중복만** 없앤다 —
   정렬하면 '처음 본 것' 이 사라진다.
3. **`as_of` 투영을 받는다.** 투영하지 않으면 2월 판정이 9월에 처음 본 MAC 을 말한다
   (불변 규칙 4). **날짜가 없는 주소는 남긴다** — 모르는 것을 '이후에 생겼다' 로 읽지
   않는다 (불변 규칙 2).
4. **`declared` 는 주소로 켜지지 않는다.** `Network.declared` 는 '네트워크를 조사했는가'
   이고 `has_remote_access` 를 거쳐 H04 에 들어간다. 주소만 있는 블록이 이걸 켜면
   **조사하지 않은 것이 '원격접속 없음' 으로 붕괴한다.** `services`·`remote_access`·
   `observed_peers` 중 하나가 있어야 켜진다.
5. **캡처와 자산을 추측으로 잇지 않는다.** 캡처가 아는 것은 IP, 자산을 아는 것은
   주문번호다. 잇는 근거는 **토폴로지가 선언한 `asset_id`** 하나뿐이다 — 제조사가
   같다는 것은 근거가 아니다(같은 제조사 장비가 수십 대다). 캡처가 만든 토폴로지는
   `node_id` 가 곧 IP 이고, 손으로 만든 토폴로지는 이름이라 `evidence.ip` 로 적는다.
   둘 다 **사용자가 적은 선언**이다.
6. **못 이은 것을 숫자로 말한다.** "어느 자산인지 모르는 주소 N개" 를 찍는다. 조용히
   넘어가면 사용자는 전부 이어진 줄 안다.
7. **MAC 이 여럿이면 붙이지 않는다.** 라우터 너머라 그 MAC 은 이 장비의 것이 아니다
   (ADR-039 와 같은 규율). IP 만 제안하고 MAC 은 뺀다.
8. **덮어쓰지 않고 더한다** (불변 규칙 3). 같은 `(ip, mac)` 이 이미 있으면 아무것도
   하지 않는다 — 같은 캡처를 두 번 넣어도 목록이 불어나지 않는다.
9. **기본은 dry-run.** `otai capture --topology <t.json>` 은 제안만 찍고,
   `--apply-addresses --assets <디렉터리>` 를 줘야 자산 파일에 더한다.

**재현성 확인**: 주소는 적용성 입력이 아니므로 `_compute_input_hash` 에 들어가지
않는다. 주소를 더하기 전후로 `otai decide` 를 돌려 `input_hash` 가 `6c5e65b3219375db`
로 **동일함**을 확인했고, 전용 테스트가 이걸 고정한다.

**결과**: CISA 고우선 14개 중 **9 → 12**.

| | 전 | 후 |
|---|:--:|:--:|
| IP address | ❌ | ✅ 스키마 · 캡처/CSV 자동 수집 |
| MAC address | ❌ | ✅ 스키마 · 캡처/CSV 자동 수집 |
| Hostname | ❌ | ⚠️ **스키마만** — CSV 로 넣을 수는 있으나 자동 수집원이 없다 |
| VLAN (중간) | ❌ | ✅ 스키마 · 캡처/CSV |

**호스트명에 자동 수집원이 없는 이유**: DHCP·mDNS·NetBIOS 를 읽어야 하는데 ADR-039
에서 다음 판으로 미뤘다. 스키마에 자리는 만들되 **✅ 로 세지 않는다** — 빈 칸을 채운
것으로 세면 그게 바로 이 프로젝트가 피하는 종류의 거짓이다.

**넣지 않은 것**: `Logging` 과 `User accounts` (고우선 2개). 이 둘은 **구성·점검 사실**
이지 자산 식별 정보가 아니다. 빈 필드를 만드는 것은 격차를 닫는 것이 아니라 칸을
만드는 것이라, 쓸 데이터원이 생길 때 넣는다. 그래서 12/14 이지 14/14 가 아니다.

## ADR-041 · 공개 전 점검 — 테스트가 통과해도 결함은 있다

**요청**: "GitHub 에 올려야 하니 결함이 없는지 체크해 달라."

**전제**: 테스트 442건·브라우저 검사 105건이 전부 통과하는 상태였다. 이번 세션 내내
그 상태에서도 결함을 계속 찾았으므로(ADR-037~040), '통과' 를 근거로 삼지 않고
**낯선 사람이 클론해서 README 대로 하면 무슨 일이 생기는가**를 실측했다.

### 찾아서 고친 것

**1. 같은 모델 장비가 자산 하나로 합쳐졌다 (false safe 급).** 실증: 같은 주문번호의
PLC 5대(펌웨어 V2.0~V2.4) → `repo.put` 5번 → 자산 **1개**, 남은 것은 마지막 V2.4.
취약한 V2.0 4대가 조용히 사라진다. 공장에서 같은 모델 여러 대는 예외가 아니라
기본이다. 원인은 `suggested_asset_id()` 가 주문번호만으로 id 를 만든 것.
화면에서는 React 행 키까지 겹쳐 체크박스 하나가 다섯 개를 한꺼번에 켰다.

고침: id = 주문번호 + **엔지니어가 붙인 장비 이름**(`Name="PLC_1"`). AML 중첩형에서는
이름이 두 단계 위(`<InternalElement Name="CPU_1"><Attribute Name="OrderNumber">`)에
있으므로 조상 Name 을 내려보내되 속성 이름표는 건너뛴다. 이름이 없으면 파일 안
위치(`member#ipath`)의 짧은 해시 — 같은 파일을 다시 넣으면 같은 id 다. **순번만으로는
만들지 않는다** — 앞 장비를 지우면 번호가 밀려 판정 이력이 고아가 된다. 그래도
겹치면 `-2` 를 붙이고, **같은 모델이 몇 대인지를 데이터로 싣는다** — 사용자가
"이름으로 구분됐다" 는 것을 알아야 한다.

**2. 의존성이 선언되어 있지 않았다.** `pyproject.toml` 이 `cryptography` 하나만 선언하는데
코드는 `fastapi`·`uvicorn`·`psycopg` 를 쓴다. README 의 첫 명령 흐름이 낯선 기계에서
`from .api import` 의 **원시 ImportError** 로 죽는다. `.[web]`·`.[dev]` extra 로 선언하고,
없을 때는 설치 명령을 말한다. **깨끗한 venv 두 개로 실증했다** — `.[web]` 을 넣으면
돌고, 안 넣으면 traceback 대신 안내가 나온다.

**3. 절대경로가 박혀 있었다.** `scripts/check_ui.py` 의 `Path("C:/Users/.../modbus")`.
README·내부 작업 지침·DECISIONS 가 이 스크립트를 안내하는데 다른 기계에서 깨지고 사용자
이름이 새어 나간다. `Path(__file__).resolve().parents[1]`.

**4. 줄바꿈이 섞여 있었다.** CRLF 49개 · LF 23개 · **한 파일 안에서 혼용 1개**
(`otai/identity.py`). 고정하지 않으면 다른 OS 의 첫 커밋이 파일 전체를 바꾼 것처럼
보인다. `.gitattributes` 로 LF 고정, 55개 파일 정규화.

**5. 외부 JSON 다섯 곳이 `safeio` 를 건너뛰었다.** 프로젝트 규칙("`json.load` 를 직접
부르지 말 것")과 어긋나게 CSAF·KEV·ATT&CK·자산 파일·자산 시드가 `json.loads` 를
직접 불렀다. 번들은 서명을 먼저 검증하므로 위험은 낮지만, 서명은 **누가 보냈는지**를
증명할 뿐 **잘 만들어졌는지**를 증명하지 않는다 — 과중첩 JSON 하나에 죽는다.
`bounded_json_loads(bytes)` 를 추가하고 다섯 곳을 옮겼다.

**6. 문서 숫자가 낡았다.** README "테스트 270개"(실제 442), "ADR 26개"(40), 캡처·프로젝트
파일·시간 축 언급 없음. 내부 작업 지침 "ADR 36개". GitHub 첫 화면이 낡은 숫자를 말하면
나머지도 믿기 어렵다.

**7. 개인 이름·개발용 자격 증명.** 테스트의 `actor="seokhyun"` → `ot-lead`. DSN 기본값
(`otai:otai@…`)은 소스에 남되 **개발용**이라고 적고 `OTAI_DB` 환경변수로 덮어쓴다.

### 실측으로 확인한 것 (주장이 아니라 셈)

- `.gitignore` 를 **실제로 돌려봤다** — 임시 `git init` → `git add -n` → 삭제. 118개
  파일, 비밀키·Siemens·툴체인·`node_modules`·`dist`·`out`·`*.db` 새어 나온 것 0,
  CISA JSON 은 정확히 2건.
- 바이트 동일 게이트: `otai render` 2회 → `cmp` 동일 (14,919 bytes).
- `scripts/demo.py` 끝까지(번들 왕복 포함) 통과.
- 픽스처 전부 `synthetic: true`. `npm audit` 취약점 0. TODO/FIXME/디버그 잔재 0.
- `safeio` 밖에서 `ElementTree` 직접 사용 0. 번들은 서명 검증 **뒤에** 매니페스트를 파싱.
- CSV Import 는 같은 파일 안 중복 id 를 이미 올바르게 처리한다(합쳐지지 않음) —
  프로젝트 파일 경로만 문제였다.

### 사용자가 정할 것 (대신 정하지 않았다)

- **`LICENSE` 파일이 없다.** 라이선스가 없으면 법적으로 남이 쓸 수 없다. 공개 의도에
  따라 고른다 — Pretendard(OFL)·Cytoscape(MIT)·React(MIT) 의 고지는 이미 있다.
- ~~원본 기획서 `.docx` 가 루트에 있다~~ → **올리지 않기로 했다** (2026-09-27). 로컬에 두고
  `.gitignore` 로 뺐다. 정본은 `docs/SPEC_v1.0.md`.
- ~~KEV 스냅샷 두 개가 커밋된다~~ → **옛 스냅샷(2026.09.08)은 올리지 않는다.** 코드는
  최신만 쓰고, 옛것은 과거 판정 재현용으로 로컬 보관한다 (CISA 는 현재 판만 배포하므로
  지우면 다시 못 받는다).
- **내부 작업 지침 파일은 올리지 않는다.** 공개 문서는 README 와 `docs/` 로 한다. 그 안의
  '코드를 고칠 때 깨지 말아야 할 것' 은 각 ADR 의 기각·한계 항목에 근거와 함께 있다 —
  README 의 문서 표가 그쪽을 가리킨다.

### 남은 한계

  나왔다(관측 시각 조작, 레벨 0.0 붕괴, 어휘 불일치, 동일 모델 합쳐짐). 공개 뒤에도
  같은 일이 생길 것이라고 보는 것이 정확하다.
- `encrypted` 불리언 하나로 OPC UA 의 혼합 보안정책을 표현 못 하는 것(ADR-040),
  프로토콜 식별 대화 미해석(ADR-039), 실제 현장 캡처·프로젝트 파일로 검증 못 한 것
  (ADR-038/039)은 그대로다.

## ADR-040 · 프로토콜 어휘 — 목록에서 빠지는 것이 이 모듈의 false safe 다

**질문에서 시작했다**: "지금은 Modbus/TCP 만 기준으로 되어 있나요?"

**답은 아니다** — 그리고 실측이 그것을 보여준다. 취약점 판정은 프로토콜을 **아예 보지
않는다**: `applicability.py` · `identity.py` · `versions.py` 세 파일에서 `protocol` 이라는
낱말이 **0번** 나온다. CSAF 는 제품 기반이라 제조사 367종 · 제품 10,381건이 그대로
대상이다. `modbus` 는 프로젝트 폴더 이름일 뿐이다.

프로토콜을 보는 곳은 둘뿐이다 — `exposure.py`(표 4 의 노출 패턴)와
`capture.py`(PCAP 식별). **그런데 그 둘의 어휘가 어긋나 있었다:**

```
캡처는 알지만 노출 위험이 모름 → ethernet_ip_io, opcua
노출 위험만 아는 것            → cip, modbus, opc_da
```

`opcua` 가 문제였다. `exposure.CONTROL_PROTOCOLS` 에는 `opc_da` 만 있어서 **자산에
`opcua` 라고 적으면 노출 위험에서 조용히 빠졌다.** OPC UA 는 현장에서 가장 흔한
프로토콜 중 하나다. 화면에 아무것도 안 뜨니 '괜찮구나' 로 읽힌다 — 이 제품이 가장
피하려는 종류의 누락이고, **목록에서 빠지는 것이 이 모듈의 false safe 다.**

정규화도 약했다. `.lower().replace("-", "_")` 뿐이라 `OPC UA` 처럼 **띄어 쓰면 못
알아봤다.** 사람이 CSV 에 손으로 적는 값이라 표기가 제각각인 것이 정상이다.

**결정**

1. `CONTROL_PROTOCOLS` 를 10종에서 **29종**으로 넓혔다. 담는 기준은 하나 —
   **공정 제어 명령이나 로직을 실어 나르는가.** IEC 61850(MMS·GOOSE) · EtherCAT ·
   HART-IP · FINS(Omron) · SLMP·CC-Link(Mitsubishi) 등이 들어왔다.
2. **SNMP·NTP·HTTP 는 넣지 않았다.** SNMP 로 설정을 바꿀 수는 있지만 공정 제어
   명령은 아니다. 넓히다가 관리 프로토콜을 넣으면 **없는 노출을 만든다** — 반대
   방향의 오류이고, 전용 테스트가 그것도 막는다.
3. `normalize_protocol()` 하나로 모았다. 공백·하이픈·슬래시·점을 `_` 로 접고 별칭
   표를 태운다 — `OPC UA` · `opc-ua` · `OPCUA` · `opc/ua` 가 모두 `opc_ua` 가 된다.
   **원문은 그대로 둔다**(불변 규칙 5) — 비교할 때만 쓴다.
   정규화가 두 호출부에 복사돼 있었는데 한 곳으로 합쳤다. 흩어져 있으면 한쪽만 고쳐진다.
4. `capture.py` 도 **같은 이름**을 쓴다 (`opcua` → `opc_ua`). 여기서 이렇게 부르고
   저기서 저렇게 부르면 또 어긋난다.
5. **불변량을 테스트로 고정했다**: 캡처가 제어용이라 부른 프로토콜은 반드시
   `is_control_protocol()` 이 알아야 한다. **한 방향만** 요구한다 — 반대는 정상이다
   (`opc_da` 는 DCOM 기반이라 고정 포트가 없어 캡처가 못 찾고, `modbus`·`cip` 는
   사람이 적는 표기다). 같아지길 요구하면 별칭을 못 쓴다.
6. `terms.ts` 에 `PROTOCOL` 표를 두어 **화면은 사람 말로** 보여준다 — `s7comm` 이
   아니라 "Siemens S7 · Siemens PLC 를 읽고 쓰는 통신". ADR-035 의 연장이고,
   엔진 이름은 그대로 둔다. 모르는 프로토콜은 **원문 그대로** 두고 지어내지 않는다.

**검증** (주장하지 않고 센다)

- `tests/test_protocols.py` 45건 — 어휘 일치 불변량 · 표기 14종 정규화 ·
  관리 프로토콜 11종이 제어로 안 잡히는지 · **평문 `OPC UA` 자산이 실제로 발견으로
  올라오는지**(목록만 고치고 판정이 안 바뀌면 의미가 없다) · 암호화된 OPC UA 는
  평문 노출이 아님 · `encrypted=None` 은 발견이 아니라 질문(ADR-035).
- 브라우저 검사에 "프로토콜을 사람 말로 보여줌" 추가 — `s7comm` 이 화면 본문에
  나오면 실패한다.

**남은 한계**

- 이 목록은 **손으로 추린 것**이다. 현장에서 쓰이는 제어 프로토콜은 더 많고,
  빠진 것은 여전히 조용히 빠진다. 파일럿에서 실제 자산 목록을 받으면 그때
  실측해서 넓혀야 한다 — 추측으로 미리 넓히지 않는다.
- 노출 판정은 여전히 **자산에 적힌 값**에 의존한다. 캡처에서 본 프로토콜을 자산의
  `services` 로 자동 반영하지는 않는다 (그건 ADR-039 의 '레벨·구역은 사람이 채운다'
  와 같은 이유로 사람 확인을 거쳐야 한다).
- **`encrypted` 는 서비스당 불리언 하나다.** OPC UA 는 한 포트에서 `None` 과
  `Basic256Sha256` 을 동시에 광고할 수 있어서 "일부 엔드포인트만 평문" 을 표현하지
  못한다. `encrypted: true` 라고 적힌 OPC UA 장비가 실제로는 `None` 정책 엔드포인트를
  열어 두고 있을 수 있다. 지금은 모델링하지 않는다 — `encrypted=None` 이 질문이 되는
  것(ADR-035)이 그나마 정확한 기본값이다.

## ADR-039 · 캡처 파일 — 토폴로지가 처음으로 합성이 아니게 된다

**맥락**: 상용 제품(Claroty·Nozomi·Dragos 계열)과 이 제품의 가장 큰 차이는
**그쪽은 트래픽에서 자산과 토폴로지를 스스로 만든다**는 점이었다. 실측하면 그 격차가
숫자로 보인다 — 토폴로지 픽스처 1개, 엣지 17개가 **전부 `state: None`**, `observed`
가 하나도 없음. 도달성이 TRUE 가 못 되니 **H01~H03 이 한 번도 발화하지 못했다.**

이건 규칙 위반이 아니다. 불변 규칙 6 이 금지한 것은 *능동* 스캔이고, 수집 우선순위에
`수동 PCAP` 이 4순위로 이미 들어 있다. 즉 ADR-038 의 프로젝트 파일과 **같은 사다리의
다음 칸**이다 — 사용자가 파일을 주고, `safeio` 가 읽고, 장비에는 접속하지 않는다.

### 먼저 고쳐야 했던 것: 레벨 미상이 `0.0` 이 되고 있었다

`load_topology` 가 `float(n.get("purdue_level", 0))` 이었다. 레벨을 안 적은 노드가
조용히 **0.0(물리 제어 계층)** 이 되고, `critical_nodes()` 가 `<= 0.0` 으로 제어
장비를 찾으므로 **모르는 노드가 전부 안전 핵심 표적**이 된다. 캡처에서 만든 노드는
레벨을 모르므로 이대로면 첫 파일에서 터진다. `Optional[float]` 로 바꾸고 `None` 은
세지 않는다 — 불변 규칙 2 의 그래프 판이다.

### 방어: 이 제품이 받는 가장 위험한 입력

XML 은 파서가 표준 라이브러리였지만 여기서는 **우리가 직접 바이트를 센다.** 길이
필드는 전부 남이 쓴 값이다. `dpkt`·`scapy` 를 넣지 않았다 — 형식이 단순해 직접 읽을
수 있고, 폐쇄망에서 의존성 하나가 곧 번들 하나다 (ADR-038 과 같은 이유).

막는 것: 매직 바이트로 형식·바이트 순서 확정(확장자를 믿지 않는다) · 파일 크기와
패킷 수 상한 · `incl_len > orig_len` · 파일 끝 초과 · 거대 snaplen · **pcapng 길이 0
블록(무한 루프)** · 블록이 파일을 넘는 경우 · `blen` 이 최소 32 미만인 패킷 블록
(안 막으면 `UnsafeInput` 이 아니라 `struct.error` 로 터진다) · 정렬 패딩과 뒤쪽 길이
필드 자리까지 계산.

`if_tsresol` 도 읽는다. 안 읽고 마이크로초로 가정하면 나노초 캡처의 시각이 1000배
어긋나고, 그 값이 화면에 그대로 나간다.

### 설계 결정

1. **`observed` 엣지만 만든다.** 캡처는 **시간 창**이다. 10분 동안 안 보였다고 경로가
   없는 것이 아니다. `inferred` 를 만들려면 서브넷을 알아야 하는데 /24 는 관습이지
   사실이 아니다. 없는 쌍을 어떻게 볼지는 **경로 엔진이 정한다** (ADR-014).
   화면이 "이건 그 시간 동안 보인 것입니다" 를 크게 싣는다.
2. **레벨·구역은 비운다.** 패킷에 없는 엔지니어링 지식이다. `unknown_level_nodes()`
   가 이걸 찾아 사용자에게 묻는다. 채우기 전에는 도달성이 확정되지 않는다 —
   그게 정확한 상태다.
3. **종류는 힌트지 사실이 아니다.** "502 를 듣고 있으면 PLC" 는 추측이므로
   `node_type` 이 아니라 `evidence["type_hint"]` 에 **근거와 함께** 넣는다.
   `_VERSION_HINT`(ADR-038)와 같은 규율이다.
4. **방향은 SYN 으로만 안다.** '포트 번호가 작으면 서버' 같은 관습은 OT 에서 자주
   틀린다. SYN 이 캡처 창에 없으면 `direction_known: false` 다.
5. **제조사는 MAC OUI 로, `Inferred` 를 넘지 않는다.** 랜카드 제조사이지 모델이
   아니다. 표는 전체 IEEE 목록이 아니라 OT 벤더만 손으로 추린 것이고, 없으면 `미상`
   이다. **MAC 이 여럿이면 라우터 너머라 제조사를 귀속하지 않는다.**
   그리고 이것만으로 **자산을 만들지 않는다** — 노드에 붙는 단서일 뿐이다.
6. **왕복은 대화 하나로 접는다.** TCP 응답이 임의 포트로 향하는 별도 엣지를 만들어
   토폴로지가 실제의 두 배로 복잡해 보였다. 서로가 상대의 출발지 포트로 보내고
   있으면 같은 대화이고, 방향은 SYN → 알려진 프로토콜 포트 순으로 정한다.
   **둘 다 없으면 접지 않는다** — 모르는 것을 정리해 버리는 것이 곧 없는 사실을
   만드는 것이다.
7. **못 읽은 것은 숫자로 말한다.** 링크 종류가 다르거나 헤더가 짧거나 조각난 패킷은
   이름 붙은 계수기로 세어 화면에 올린다. 조용히 건너뛰면 "우리 망은 조용하구나"
   로 읽힌다.

### 이번 판에서 하지 않은 것

- **프로토콜 식별 대화 해석** (CIP `List Identity`, S7 SZL, Modbus FC43/14).
  여기서 정확한 모델과 펌웨어가 나오고, 그것은 **장비가 직접 답한 값**이라
  프로젝트 파일의 설정값과 달리 진짜 관측이다. 다만 스펙을 보고 바이트 배치를
  써야 하고 실제 캡처로 검증할 수 없으므로, 프로토콜 하나씩 각자 픽스처와 함께
  붙인다. **그때까지 캡처가 버전을 '확인' 한다고 말하면 안 된다.**
- **LLDP·ARP·DHCP·mDNS** — 이름과 이웃 관계가 나오지만 같은 이유로 다음 판.
- **IPv6** — 현장 OT 에서 드물고, 지금 넣으면 검증 못 한 코드가 는다.

### 남은 한계 (주장하지 않는 것)

- **가만히 있던 장비는 안 보인다.** 캡처 중 통신이 없으면 존재 자체를 모른다.
- **정상 운영 캡처에는 식별 대화가 잘 없다.** `List Identity`·SZL 은 보통 엔지니어링
  툴이 접속할 때만 오간다. 현실적 수확은 **제조사 + 토폴로지**다.
- **암호화된 트래픽**은 양 끝점만 주고 식별은 못 준다.
- **실제 OT 캡처로 검증하지 못했다.** 합성 캡처와 공개 형식 규격으로 만들었다.
  ADR-038 과 같은 제약이고, 파일럿 현장의 캡처가 생기면 그때 확인해야 한다.
### 검토에서 고친 것

- **토폴로지 JSON 이 `safeio` 를 안 거치고 있었다.** 픽스처가 1차 자료일 때는 문제가
  아니었지만, 이번 판이 **사용자가 파일을 내려받아 손으로 고쳐 되돌려주는 흐름을
  열었다.** 초안에 "다음 판" 이라고 써 놓고 그 문을 연 셈이라 지금 닫았다 —
  `load_topology` 가 `bounded_json_load` 를 쓴다.
- **`unknown_level_nodes()` 를 아무도 부르지 않았다.** 레벨이 빈 파일을 주고
  "사용자가 채우세요" 라고만 하면 채울 방법이 없다. `otai capture` 가 **채워야 할
  노드 이름을 대고**, `otai paths` 가 레벨 미상이 있으면 "도달성이 확정되지
  않습니다" 를 먼저 찍는다. 화면에는 내려받기 단추가 있고 검사가 확인한다.
- **종류 힌트가 '듣고 있으면 PLC' 를 먼저 봤다.** 작업용 PC 도 도구용으로 제어
  포트를 열어 둔다. OT 에서 더 강한 신호는 **팬아웃** — 여러 제어 포트로 거는 쪽이
  작업용 PC 다. 여전히 힌트이지만 덜 틀린다.

## ADR-038 · 프로젝트 파일 — 스키마를 추측하는 대신 방향을 뒤집는다

**요청**: "프로젝트 파일 파서를 사용자가 제공해주면 그 때 읽어서 미상을 줄이는걸로
하면 어떤가요?"

**답**: 맞다. 그리고 기획서가 이미 그렇게 말하고 있다 — 불변 규칙 6 의 수집
우선순위에서 `프로젝트 백업` 은 3순위이고 능동 스캔은 기본 금지다. 사용자가 파일을
주는 방식은 **장비를 건드리지 않는다**. CSV Import 와 같은 dry-run·확인 모양을 쓰면
추측 금지도 지켜지고, 파일 해시가 거기서 나온 모든 값의 출처가 되어 계보도 선다.

### 막고 시작한 것 두 가지

**1. XML 방어가 아예 없었다.** `otai/` 안에 XML 파서가 한 줄도 없었으므로 XXE·엔티티
폭탄 방어도 없었다. 실측:

| 공격 | `ElementTree` 기본 동작 |
|---|---|
| 외부 엔티티(XXE) | **거부** — 정의되지 않은 엔티티로 본다 |
| 내부 엔티티 폭탄 | **통과** — 5단계에서 347바이트가 100만 자가 됐다 (2,882배) |
| 중첩 5만 단계 | **통과** — 깊이 제한이 없다 |

둘 다 DTD 가 있어야 성립한다. 그래서 **DTD 를 문 앞에서 거부한다**. 설비 도구의
내보내기 형식(AutomationML·TIA·PLCopen)은 DTD 를 쓰지 않으므로 잃는 입력이 없다.
`defusedxml` 은 넣지 않았다 — 의존성이 `cryptography` 하나뿐인 것은 폐쇄망 배포를
위한 선택이고(불변 규칙 9), DTD 거부는 그 라이브러리보다 **강한** 조치다.

프롤로그만 훑는다. 본문에 `&lt;!DOCTYPE` 같은 글자가 있다고 멀쩡한 파일을 거부하면
안 된다 — 처음 구현은 프롤로그 끝을 DOCTYPE **앞**으로 잡아서 폭탄을 통과시켰다.
`tests/test_adversarial.py` 가 숨는 자리 넷(소문자·주석 뒤·BOM 뒤·공백 뒤)을 다 찔러본다.

**2. 설정값을 관측값으로 쓰면 false safe 다.** 프로젝트 파일의 펌웨어는 **그 프로젝트가
대상으로 설정한 값**이지 장비에서 읽은 값이 아니다. 장비를 교체했거나 현장에서 따로
올렸으면 프로젝트는 그대로여도 실제는 다르다. 이 값으로 `fixed`·`비영향 확인`·
`적용 확인` 에 도달하면 **아무도 관측하지 않은 버전으로 안전을 선언**하게 된다.

`applicability.CLAIMED_METHODS = ("project_file",)` 이 이걸 막는다. 후보 수준 식별에
이미 걸어둔 것과 같은 종류의 방어를 버전 축에 건 것이다:

| 상황 | 관측값일 때 | 설정값일 때 |
|---|---|---|
| 범위 **안** | 적용 확인 | **적용 가능성 높음** |
| 범위 **밖** | 비영향 확인 | **정보 부족** (+ 실제 버전을 묻는 질문) |
| 패치 증거 있음 | 수정 확인 | **도달하지 않음** |

식별(주문번호)은 여기 해당하지 않는다 — 그건 문서화된 현장 기록이고, 오래되면
신선도 정책이 따로 잡는다.

### 스키마를 추측하지 않는다 — 방향을 뒤집는다

TIA Portal 의 `.ap18`, GX Works3 의 `.gx3` 내부 구조는 공개되어 있지 않다. 알아낸 척하고
파서를 쓰면 그건 검증할 수 없는 코드다. 그래서 반대로 읽는다:

    프로젝트 파일에서 문자열을 거두고,
    **실제 권고문에서 뽑아 이미 들고 있는 식별자 목록**과 맞춘다.

권고문 1,306건에서 주문번호 **1,028개**(변별력 있는 것)·제품명 **4,581개**·제조사
**363곳**이 나온다. 이건 검증 가능한 근거이고 저쪽 도구의 스키마와 무관하다. XML 이든
AutomationML 이든 zip 안의 무엇이든 같은 방식으로 읽힌다.

측정으로 정한 것들:

- **변별력 없는 식별자는 사전에서 뺀다.** 코퍼스에 `110930` 같은 순수 숫자 주문번호가
  있다. XML 어디에나 나타나므로 맞춰봐야 오탐만 는다 — 글자와 숫자가 둘 다 있고
  7자 이상인 것만 쓴다 (1,181 → 1,028).
- **문서 판번호는 펌웨어가 아니다.** 첫 실측에서 `SchemaVersion="2.15"` 가 펌웨어로
  잡혔다. 이런 값이 자산에 들어가면 없는 버전을 지어내는 것이다.
- **AutomationML 의 관용형을 놓쳤었다.** `<Attribute Name="FirmwareVersion"><Value>V2.9</Value>`
  는 이름이 부모 속성에 있고 값이 자식 본문에 있다. 이름을 아래로 물려주지 않으면
  이 형태를 통째로 놓친다.
- **버전은 이름이 아니라 거리로 묶는다.** 어느 장비의 펌웨어인지 알아야 자산에 넣는데,
  `InternalElement` 가 장비인지 `Device` 인지 알 수 없다. 주문번호가 나온 자리에서
  경로가 가장 가까운 값이 그 장비의 것이다. 같은 거리에 둘이면 **고르지 않고**
  `여럿` 으로 표시한다 — 하나를 임의로 고르면 없는 사실을 만드는 것이다.

### 기각한 것

- **`defusedxml` 의존성 추가** — DTD 거부가 더 강하고, 폐쇄망 배포에서 의존성 하나가
  곧 번들 하나다.
- **`python-multipart` 로 파일 업로드** — 같은 이유. 파일은 base64 로 JSON 본문에 담는다.
- **`.ap18`·`.gx3` 독자 형식 파서** — 검증할 수 없는 코드다. 못 읽는다고 **말한다**:
  "도구에서 AutomationML(.aml) 또는 XML 로 내보낸 뒤 주세요." 조용히 빈 결과를 주지 않는다.
- **찾은 값을 자동으로 자산에 쓰는 것** — dry-run 이 기본이고 사람이 고른 것만 들어간다.
- **자산의 구역·안전등급·원격접속을 프로젝트 파일에서 추론하는 것** — 그 파일에 없는
  정보다. 비워 두면 화면이 `미상` 으로 보여주고 다음 질문이 그것을 묻는다.

### 사용자 요청 문구에 대한 정정

"미상을 줄인다" 는 **식별에만** 해당한다:

| | 프로젝트 파일이 하는 일 |
|---|---|
| 식별 미상 | 줄어든다 — 주문번호가 나오면 Fuzzy → **Exact** |
| 랙 구성 | CPU·통신모듈을 나눠 담을 수 있다 (기획서가 요구하는 분해) |
| **버전 미상** | **확인으로 바뀌지 않는다** — "설정값은 X, 실제값은 미상" 이 된다 |

화면이 이 문장을 그대로 싣는다. 등급만 조용히 낮추면 아무도 모른다.

### 실측 (자산 2대를 실제로 등록해 확인)

AutomationML 한 장에서 장비 2대를 알아보고 등록한 뒤 판정하면
**적용 가능성 높음 5건 · 정보 부족 4건**이 나온다. `적용 확인`·`수정 확인`·
`비영향 확인` 은 **0건** — 가드가 실제 시스템에서 작동한다.

### 검토에서 고친 것

- **관측 시각이 업로드 시각이 되고 있었다.** 웹으로 받은 바이트를 임시 파일에 쓴 뒤
  그 파일의 mtime 을 읽었으므로, 2023년에 저장한 프로젝트가 2026-09-11 에 관측된
  것으로 기록됐다. 이 ADR 이 안 하겠다고 쓴 바로 그 일이고, 파일시스템을 통해
  시계 금지 규칙을 우회한 것이기도 하다. 이제 브라우저가 `File.lastModified` 를
  함께 보내고, 압축 파일은 **멤버의 저장 시각**을 쓴다(복사·업로드로 바뀌지 않는다).
- **버전을 비교하지 못했을 때 "범위 밖" 이라고 말하고 있었다.** 상태는 맞았지만
  설명이 거짓이었다. 이 제품이 파는 것은 상태가 아니라 설명이다.
- **주문번호를 공백까지 맞춰 보고 있었다.** Siemens 카탈로그는 `6ES7 518-…` 처럼
  띄어 쓰고 코퍼스에는 붙여 쓴 것이 들어 있다 — 실제 내보내기 파일에서 Siemens
  장비를 하나도 못 알아볼 수 있었다. 다만 **TIA 의 AML 이 정확히 어떤 표기로 쓰는지는
  확인하지 못했다.** 공백을 지우고 맞추는 것은 7자 이상·글자숫자 혼합이라는 조건
  아래에서 오탐을 만들지 않으므로, 확인 전까지의 안전한 쪽으로 골랐다.
- **'모델' 칸에 주문번호를 다시 박고 있었다.** 사용자가 이미 지적한 그 문제다.
  사전이 제품명을 함께 든다.
- **자산 만들기가 CLI 와 API 두 곳에 있었다.** `method="project_file"` 표시가 가드를
  켜는 스위치인데 두 곳에 있으면 한쪽만 고쳐져 조용히 어긋난다. `to_asset()` 하나로.

### 남은 한계

- GX Works3 는 표준 내보내기가 덜 정리되어 있다. CSV·텍스트 내보내기는 기존
  `csvimport` 로 가고, 독자 형식은 읽지 못한다고 말한다.
- 프로젝트가 담은 **연결 관계**(장비 간 통신)는 아직 거두지 않는다. 토폴로지의
  `inferred` 엣지로 쓸 수 있지만, 엣지를 잘못 만들면 경로 판정이 거짓으로 이어진다
  (ADR-014). 별도 판단이 필요해 이번 판에서는 하지 않았다.
- 주문번호가 우리 목록에 없으면 알아보지 못한다. 코퍼스가 넓어지면 같이 넓어진다 —
  추측으로 메우지 않는다.

## ADR-037 · 시간 축 — 그 시점에 알려져 있던 것만으로 판정한다

**발견한 결함**: `--as-of` 는 슬라이스 1 부터 있었고 재현성 게이트도 통과하고 있었다.
그런데 그 인자는 **버전 비교와 신선도에만** 걸렸을 뿐 **권고문 목록에는 걸리지 않았다**.
`--as-of 2026-02-01` 로 판정하면서 2026-08 에 나온 권고문을 함께 보고 있었다는 뜻이다.
실측하면 1,306건 중 **317건이 그 시점에 존재하지 않던 문서**였다.

같은 결함이 KEV 에도 있었다. KEV 항목은 `dateAdded` 를 갖는데 2026-09-10 스냅샷을
2월 판정에 그대로 쓰고 있었다 — **204건**이 2월 이후 등재분이다. H01 은 KEV 를
전제조건으로 쓰므로, 그때는 악용이 알려지지 않았던 CVE 로 P0/P1 이 서 있었다.

이건 기능 추가가 아니라 **불변 규칙 4(재현성)의 구멍**이다. 같은 스냅샷·같은 규칙이라도
'언제 알려졌는가' 를 빼면 과거를 재현한 것이 아니라 오늘의 지식으로 과거를 다시 읽은 것이다.

**결정**

1. `known_at(권고문, 시점)` 이 **삼진**을 돌려준다. `initial_release_date` 가 없으면
   `unknown` 이다 — 없다고 '없었다' 로 읽으면 그 문서가 다루는 취약점이 과거 열에서
   통째로 사라진다. **배제는 `false` 일 때만 한다.** 불변 규칙 2 를 시간 축에서 지키는 것이다.
2. **개정은 존재와 다른 사실이다.** 2월에 나온 문서를 8월에 고쳤다면 그 문서는 2월에
   존재했지만 우리가 든 사본은 2월의 내용이 아니다. 존재는 `true`, 내용은
   `revision_uncertain` 으로 **따로** 말한다. 하나로 뭉치면 둘 다 못 쓴다.
   실측: 2026-02-01 기준 989건 중 **103건**이 그 뒤 개정됐다.
3. `kev_at(스냅샷, 시점)` 이 `dateAdded` 로 거른다. 날짜가 비면 남긴다(같은 규칙).
4. **순회하는 자리를 하나로 모았다** — `_findings` · 스윕 · `next_question` · `_scanned`
   넷이 각자 `zip(advisories, indexes)` 를 돌고 있었다. 한 곳만 고치면 화면마다 숫자가
   달라지는데, 그게 정확히 지금 고치는 결함이다. `_at(시점)` 하나가 (보이는 권고문, 그
   시점 KEV) 를 만들고 넷이 그것을 쓴다.
5. `_scanned` 가 **세 수**를 돌려준다. '아직 안 나온 문서' 와 '이 장비 얘기가 아닌 문서' 는
   다른 사실이다. 합쳐 세면 과거 시점에서 "이 문서들이 다루는 제품이 이 장비가 아닙니다"
   라는 화면 설명이 **거짓**이 된다.
6. 두 시점 비교는 **4종**이다 — 새로 생김 / 등급 변경 / 사라짐 / **비교 불가**.
   어느 한쪽이라도 `unknown` 이거나 개정본이면 비교 불가다. 말할 수 없는 것을 '변화 없음'
   으로 접으면 시간 축에서의 false safe 다. 화면에서도 흐리게 칠하지 않는다.
7. **버킷과 상태만 비교한다.** 렌즈 점수는 보지 않는다 — 부동소수 잡음이 '등급 변경' 으로
   둔갑한다. 등급은 사실이고 점수는 같은 등급 안의 정렬일 뿐이다 (ADR-007 과 같은 선).
8. **자산은 고정이다.** 합성 자산의 `observed_at` 을 과거로 고쳐 쓰지 않는다 — 없는 역사를
   지어내는 것이고, 이 프로젝트가 합성 데이터에 대해 지켜온 선을 넘는다. 따라서 과거 열은
   '그때의 현장' 이 아니라 **'그 시점에 알려져 있던 권고문으로 지금의 자산을 다시 판정한
   것'** 이다. 화면이 이 문장을 그대로 싣는다.

**기각한 것**

- **`observed_at` 을 과거로 흩뿌려 '진짜 과거' 를 만드는 것.** 데모는 좋아지지만 없는
  역사를 지어내는 것이다. 대신 **코퍼스가 실제로 갈리는 날짜**를 기본 기준일로 골랐다
  (2026-02-01 — 989/1,306).
- **`current_release_date` 만으로 시점을 판단하는 것.** 개정된 문서가 전부 '그때 없었다'
  가 되어 과거 열이 텅 빈다. `initial` 과 `current` 는 다른 필드다 (표 13 의 시간 필드 구분).
- **시작할 때 미리 계산해 두는 것.** 전수 계산 두 번이라 45초다. 눌렀을 때만 돌고
  `(앞 시점, 뒤 시점, 정책 버전)` 으로 캐시한다 — 정책이 바뀌면 결과가 달라지므로
  날짜만으로 캐시하면 낡은 비교를 준다.

**남은 한계** (주장하지 않는 것)

- '사라짐' 은 실측 0건이다. 코퍼스가 **현재 내용만** 들고 있어서, 2월에 걸린 문서는 9월에도
  같은 내용으로 걸린다. 움직이는 것은 `as_of` 에 의존하는 입력(신선도·KEV)뿐이다.
  그래도 이 칸을 지우지 않는다 — 0 이라는 사실 자체가 정보이고, 나중에 실제 철회
  (`withdrawn`) 를 받으면 채워질 자리다.
- `decide_applicability` 는 `observed_at > as_of` 를 따로 표시하지 않는다. 과거 재현의
  남은 구멍이고, 자산 축을 시간으로 다룰 때 함께 닫아야 한다. 이번 판에서는 고치지 않았다.

**결과**: `PARSER_VERSION` 이 `csaf-2.0/2` 로 올라갔다(`initial_release_date`·개정 횟수
추가). 기본 시점(2026-09-11)에서는 1,306건 전부가 `true`·개정 없음이라 **기존 판정이
바뀌지 않는다** — 회귀 테스트가 이것을 고정한다.

## ADR-036 · 마감 — 어두운 화면에서 깊이는 테두리가 아니라 표면이 만든다

**요청**: "고가 제품처럼 고급지면 좋겠다."

**진단**: 기존 CSS 는 1px 테두리 12곳, 그림자 3곳, 전환 4곳이었다. 조사한 관행과
정반대다 — 어두운 배경에서 **1px 테두리는 약한 신호**다. 흐리면 사라지고 진하면
무겁다. 깊이는 **표면 밝기 단계**로 만들어야 한다.

**바꾼 것** (장식을 더한 것이 아니라 정밀도를 올린 것이다)

| | 전 | 후 |
|---|---|---|
| 깊이 | `border:1px solid` | 표면 4단계 + 윗면에 걸리는 얇은 빛(`inset 0 1px`) + 은은한 그림자 |
| 헤어라인 | 고정 색 `#263140` | `rgba(255,255,255,.055)` — 배경이 바뀌어도 같은 세기 |
| 상태색 | `#FF6A5E` `#FFB627` `#34C79B` | 한 단계 낮춤. **넓게 칠하지 않고 2px 선 하나로** |
| 숫자 | `tnum` | `tabular-nums lining-nums` + 자간 −.035em — 계기판처럼 |
| 움직임 | 거의 없음 | 160ms `cubic-bezier(.2,0,0,1)`, 행 호버에 1px 부상 |
| 초점 카드 | 빨간 테두리 상자 | 모서리에서 번지는 아주 옅은 빛 + 한 단계 높은 그림자 |

**명암비는 오히려 올라갔다** — 4.7:1 → 4.8:1 (브라우저에서 실측). 색을 낮추면서
표면을 정리하니 본문 대비가 좋아졌다. 검사가 이걸 지킨다.

**긴 문장 처리**: 확인할 것이 넷이면 "A, B, C, D를 확인하면 됩니다" 가 한 줄을
폭발시킨다. 셋 이상이면 **"A 등 4가지"** 로 줄이고 목록은 옆 칸에 편다. 정보를
줄이지 않고 읽는 순서를 바꾼 것이다.

**h3 의 두 가지 역할을 분리했다.** 구획 라벨(작고 자간 넓게)과 카드 제목(15.5px,
무게 650)은 다른 물건이다. 하나로 쓰면 둘 다 어색해진다.

## ADR-035 · 표 4 의 나머지 위험 객체 — 그리고 보안을 모르는 사람이 읽을 수 있는 말

**빠져 있던 것**: 표 4 는 위험을 넷으로 **분리하라**고 했는데 우리는 둘만 했다.
그래서 **CVE 가 하나도 없는 장비는 완벽해 보였다.** 평문 Modbus 를 서버로 열어둔
PLC 가 큐에 뜨지 않았다.

| 위험 객체 | 전 | 후 |
|---|---|---|
| Exposure Pattern (평문·인증 부재·쓰기 도달) | 없음 | `PLAINTEXT_CONTROL` |
| CVE | 완성 | 완성 |
| Configuration Finding (기본 계정·원격관리 노출) | 없음 | `REMOTE_ACCESS_NO_MFA` |
| Lifecycle Finding | ADR-034 | ADR-034 |

**핵심 차이**: CVE 는 고칠 수 있고 **설계 노출은 대개 못 고친다.** 전통적 Modbus TCP
에는 애플리케이션 계층 인증이 없다 (SPEC 2.2) — 펌웨어를 올려도 그대로다. 그래서
답이 '패치' 가 아니라 **보상 통제**다 (SPEC 2.3). 화면이 그 차이를 문장으로 말한다.

증명: `melsec-iqr-fw49` 는 이 CVE 에 **비영향 확인(P4)** 인데 평문 제어 통신 발견을
그대로 갖는다. 섞었다면 이 장비는 완벽해 보였을 것이다.

**등급은 계산이 아니라 표다.** 이 발견에는 CVSS 도 KEV 도 버전 범위도 없어 점수를
매길 근거가 없다. 고정 표로 정하고 그 사실을 적는다 (ADR-008 과 같은 태도).
**닿는지 모르면 `P?`** 다 — '안 닿는다' 로 단정하지 않는다. **관점(렌즈)은 이 행을
건드리지 않는다** — 가중치를 줄 대상이 없다.

**모르는 것은 발견으로 만들지 않는다.** `encrypted` 가 `None` 이면 '평문일 수도 있다'
행 대신 **질문**을 돌려준다. 그건 불변 규칙 2 가 막는 붕괴를 반대 방향으로 하는 것이다.
통신 정보가 아예 없는 장비도 조용히 넘기지 않고 물어본다.

**중복이 아니라 상호 참조**: 같은 사실이 H02 의 근거이기도 하면 CVE 행은 "이 장비가
암호 없이 명령을 받는 것이 등급을 올렸습니다" 를, 노출 행은 "위 취약점 등급도 이것
때문입니다" 를 적는다. 표 4 의 요점은 **분리 가능하다**는 것이다 — 하나는 고칠 수
있고 하나는 못 고친다.

### 보안을 모르는 사람이 읽을 수 있어야 한다

새 발견만 쉬운 말로 쓰면 **옛 행이 더 나빠 보인다.** 그래서 함께 바꿨다.

- 모든 발견에 **세 줄**을 준다: 무슨 일인가 / 그래서 뭐가 위험한가 / **지금 뭘 하면
  되나**. 세 번째가 없었고, 그게 누가 이 제품을 쓸 수 있는지를 가장 크게 바꾼다.
- 화면용 이름과 엔진 이름을 분리한다. 엔진은 `유효 경로` 를 쓰고(규칙표·테스트·근거
  기록이 그 이름을 쓴다), 화면은 "밖에서 이 장비까지 길이 열려 있는지" 를 쓴다.
- 식별 사다리도 **방법이 아니라 결과**로 쓴다: "정규화 후 완전 일치" → "제조사와
  모델이 정확히 맞습니다".
- `scripts/check_web.py` 가 **금지어 목록**을 할 일 화면 본문에서 검사한다
  (무인증·평문·세그먼트·도달성·발화·전제조건·정규화·토큰·벡터·스냅샷·계보…).
  '자세히' 안이나 운영 콘솔에는 있어도 된다 — 거기까지 간 사람은 알고 싶은 사람이다.

## ADR-034 · 수명주기는 제조사가 1차 근거다 — 표 13 의 마지막 빈 칸을 채운다

**감사에서 드러난 것**: 표 13 의 8개 판정 필드 중 **수명주기만 데이터 경로가 아예
없었다.** `lifecycle_status` 는 자산 입력값뿐이고, 사용자가 "EOL" 이라 적으면 그대로
믿고 그 값으로 **H04 강제규칙이 P1 을 발화**했다. 표 13 이 1차 근거로 지목한 제조사
선언은 어디에도 들어오지 않았다.

**근거는 이미 데이터에 있었다.** CSAF 2.0 의 `remediation.category` 는 열거값이고
그중 `no_fix_planned` 는 **제조사가 고치지 않겠다고 공식 선언한 것**이다. 실측:
권고문 1,303건 중 181건에 수명주기 신호가 있고, 구조화된 주장 100건 · 문장에서 읽은
주장 47건을 뽑았다.

**결정** (`otai/lifecycle.py`)
- `no_fix_planned` → 구조화된 제조사 주장. **`none_available` 은 아니다** — '지금 쓸 수
  있는 수정이 없다' 와 '지원이 끝났다' 는 다른 사실이다. 승격하지 않는다.
- 자유 문장(`end of life`, `discontinued` …)에서 읽은 것은 **`structured=False`** 로
  표시하고 구조화된 값보다 뒤에 둔다. 문구는 오독될 수 있다.
- 권위는 표 13 대로 **제조사 > 조정기관 > 현장 기록**. 사용자가 `supported` 라고 적어도
  제조사가 `no_fix_planned` 를 선언했으면 제조사가 이기고, **갈렸다는 사실을 보존한다.**
- 근거가 없으면 `unknown` 이다. **'지원 중' 으로 붕괴시키지 않는다** (불변 규칙 2).
- `remediation.product_ids` 로 범위를 좁힌다 — 권고문 어딘가에 'no fix' 가 있다고 해서
  우리 제품이 그렇다는 뜻이 아니다.

**H04 는 이제 정리된 뷰를 본다.** 전제조건이 '제조사 확인' 인지 '현장 기록' 인지
근거 문장에 남는다. `lifecycle` 을 넘기지 않으면 예전 동작 그대로다 — 기존 호출부를
깨지 않는다.

실측 효과: 웹앱에서 H04 보류가 142건 잡힌다. 예: 자산이 `supported` 라고 적었는데
ICSA-26-174-03 이 `no_fix_planned` 를 선언해 **결론이 지원 종료로 뒤집히고 충돌로
기록된다.**

**남은 것**: 제조사 EOL/EOS 페이지는 기계가 읽을 수 있는 형태가 아니다. CSAF 안의
선언만으로는 '이 제품이 단종됐다' 를 전부 알 수 없다. 지금 채운 것은 **권고문이
말해 주는 범위**이고, 그 밖은 여전히 현장 기록에 의존한다 — 화면이 둘을 구분해 말한다.

## ADR-033 · 표에 없는 발행처는 '미확인' 이다 — 선언값으로 넘어가지 않는다

**ADR-024 의 구멍**: 발행처가 `KNOWN_PUBLISHERS` 에 없으면 `publisher_category` 를
그대로 썼다. 그건 ADR-024 가 *믿지 말라고 한 바로 그 값*이다. 표가 3곳뿐이었고
코퍼스에 발행처가 2곳(CISA·Siemens)뿐이라 **지금은 100% 표로 판단하지만, Schneider
CSAF 를 한 건만 넣어도 조용히 무너진다.**

**결정**
1. 표를 53곳으로 넓힌다 — 조정기관 11곳 + 제조사 42곳. 이름은 **코퍼스에 실제로
   나타나는 문자열**에서 가져왔다. 부분 일치라 `Siemens` 가 `Siemens ProductCERT` 를
   잡고, `Rockwell Automation` 이 `Rockwell Automation PSIRT` 를 잡는다.
2. 표에 없으면 **`unverified`**. 선언값으로 넘어가지 않는다.
3. `unverified` 는 모든 필드 권위에서 **맨 뒤**다. 검증되지 않은 출처가 검증된 출처를
   이기는 일이 없다. **값 자체는 보존되고 화면에도 보인다** — 숨기는 것이 아니라
   권위를 주지 않는 것이다.
4. 조정기관을 제조사보다 먼저 대조한다. 조정기관 이름 안에 제조사 이름이 들어갈 수 있다.

**쓰지 않기로 한 규칙**: "발행처 이름이 제품 제조사와 같으면 vendor" 는 매력적이지만
실측에서 CISA 권고문 1,301건 중 2건이 제품 제조사를 문자 그대로 `CISA` 로 적어
오탐이 났다. 권위를 정하는 판단에 1/650 오탐은 크고, **틀리는 방향이 조용하다.**
증거로 보이지만 증거가 아니었다.

**운영 콘솔이 그 수를 보여준다** — 권위 미확인 권고문이 몇 건이고 어느 발행처인지.
0이 아니면 표를 넓혀야 한다는 뜻이고, 그건 사람이 확인할 일이다.

## ADR-032 · '값이 여럿' 은 충돌이 아니다 — 충돌은 겹치는 범위에 대한 불일치다

**발견**: 출처 대조 화면이 "값이 다른 것 223건" 을 보여주고 있었다. 실측해 보니
**192건(86%)이 한 권고문 안에서 같은 제품에 범위를 여럿 적은 것**이었다. 출처가
하나인데 충돌로 셌다. 원인은 한 줄이다:

```python
conflicting = len(values) > 1      # 출처를 보지 않는다
```

7.2 가 말하는 충돌은 *"벤더와 NVD의 영향 범위가 다르면"* 이다 — **서로 다른 출처가
같은 사실을 다르게 말하는 것**이다. 한 출처가 주문번호 하나에 여러 `product_id` 를
두고 각각 범위를 다는 것은 CSAF 에서 흔하고 정상이다.

**결정**: 넷으로 나눈다.

| 상태 | 뜻 | 실측 (제품 2,177건) |
|---|---|---:|
| `conflicting` | 출처가 다르고 **범위가 겹치는데** 값이 다르다 | **28건** |
| `disjoint` | 출처는 다른데 범위가 겹치지 않는다 — 다른 분기 | 0건 |
| `undecidable` | 범위를 파싱하지 못해 겹침을 알 수 없다 | 2건 |
| `multivalued` | 한 출처가 값을 여럿 말한다 | 193건 |

**겹침 판정은 `versions.py` 로 한다.** 파싱에 실패하면 충돌이라고 단정하지 않고
`undecidable` 로 둔다 — **비교에도 삼진 논리를 적용한다** (불변 규칙 2). 모르는 것을
충돌로 밀어 올리면 H05 가 잘못 발화하고, 그건 반대 방향의 거짓 경보다.

**'채택' 하나만 보여주지 않는다.** 값이 여럿일 때 `current` 는 정렬 첫 값이라 논쟁과
무관한 값이 나올 수 있다. `FieldView.disputed` 가 **실제로 부딪히는 값 쌍**을
(값A, 출처A, 값B, 출처B) 로 들고 다니고 화면이 그것을 보여준다.

실제로 잡힌 것 하나: `RTU500 series CMU Firmware` 를 ICSA-26-062-03 은
`>=13.6.1|<=13.6.2` 로, ICSA-26-155-04 는 `>=13.6.1|<=13.6.3` 으로 말한다. 겹치는데
다르다 — 나중 권고문이 영향 범위를 넓혔다. 이것이 7.2 가 상정한 바로 그 상황이다.

**H05 는 아직 이 값을 쓰지 않는다.** `source_conflict` 는 여전히 호출자가 넘기는
인자다. 연결하려면 (자산 → 그 자산에 걸린 묶음 → 충돌 여부) 경로가 필요하고,
그건 별도 작업이다. 지금 연결하면 가짜 충돌 192건이 H05 를 대량 발화시켰을 것이다 —
정의를 먼저 고친 것이 순서상 맞다.
